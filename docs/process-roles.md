# Роли процесса `pulsed`: `dns`, `api`, `all`

Разделение нужно, чтобы REST API не голодал под DNS-нагрузкой: DNS- и
API-транспорты живут в разных процессах, а единственный источник истины —
один и тот же v2-zonefile, открытый в multi-process режиме (ADR 0007).

## Режимы

| `role` | Zonefile | Транспорты | Journal | Поведение |
|---|---|---|---|---|
| `all` (по умолчанию) | single-process (`LOCK_EX`) | DNS + REST | да | текущее поведение, один процесс |
| `dns` | multi-process (`LOCK_SH` + lease) | только DNS | нет | читает зоны из mmap, опрашивает новые версии |
| `api` | multi-process | только REST | да | создаёт/меняет зоны и rrset'ы |

`dns` и `api` могут одновременно работать на одном файле. Второй `all` на
занятом файле завершается с `v2 zone file is busy` (код выхода 2).

## Запуск

```bash
# Один раз создайте файл зон (или позвольте это сделать роли api).
pulsed import --data /tmp/pulse-dns.zonefile --origin example.com. example.com.zone

# DNS-процесс
pulsed --config examples/pulsed-dns.toml

# REST-процесс
PULSED_API_TOKEN='...' pulsed --config examples/pulsed-api.toml
```

CLI-эквиваленты: `--role dns|api|all`, `--dns-workers N`, `--api-workers N`,
`--zone-poll-ms MS`.

## Видимость изменений

* REST-мутация коммитится в zonefile под lease зоны.
* Роль `dns` читает голову зоны из файла при каждом ответе, поэтому новые
  rrset'ы видны сразу после коммита.
* Новые/удалённые зоны и метаданные каталога подхватываются фоновым опросом
  (`zone_poll_ms`, по умолчанию 250 мс) без полной перезагрузки: перечитывается
  каталог, перестраиваются только изменившиеся view.
* API-записи, таким образом, видны DNS в пределах одного интервала опроса
  (≤ 1 с при настройках по умолчанию).

## Журнал и отказоустойчивость

* Write-ahead journal открывает и восстанавливает только роль `api`.
* `kill -9 api`: DNS продолжает отвечать; при рестарте `api` незавершённые
  интенты переигрываются один раз (идемпотентно).
* `kill -9 dns`: API продолжает принимать мутации; рестарт `dns` видит всё,
  что было записано в файл.
* `fsck`/`repair` по-прежнему запускаются офлайн, когда живых процессов нет.

## Ограничения

* Каталог зон (`create_zone`/`delete_zone`/метаданные) должен менять один
  процесс (M3-L1): на практике это роль `api`; роль `dns` каталог только читает.
* Durable-фаза коммитов сериализуется глобальным commit-lock: потолок
  throughput — `fdatasync` одного inode (M3-L2).
* Рекламация страниц в multi — bump-only до quiescent-окна (PW-L13).
* `dns_workers` задаёт число UDP/DNSCrypt worker'ов. `api_workers` — лимит
  одновременных REST-соединений (на соединение — один поток),
  `api_rate_limit_per_sec` — token bucket на токен (по умолчанию 100).
* Явные affinity-списки ядер не реализованы: изоляция достигается отдельными
  процессами и планировщиком ОС (при необходимости — `taskset`/cgroup).
* `dns`-процесс не подписывает зоны и не запускает secondary/rotation: это
  делает `all`-процесс или REST `/sign`.

## Замеры

`cargo bench -p pulsed --bench role_split -- --seconds 5`, 8 vCPU (SMT, общие),
8 DNS-клиентских потоков, 8 потоков REST PUT, `durability=flush`, journal
выключен, 8 зон:

| Сценарий | DNS qps | DNS p50 / p99 | REST PUT/s | REST p50 / p99 |
|---|---|---|---|---|
| `all` (один процесс) | 98k–106k | 53–58 µs / 355–405 µs | 381–385 | 21.8 ms / 27–28 ms |
| `split` (`dns`+`api`) | 85k–93k | 58–59 µs / 534–659 µs | 359–361 | 22.1–22.3 ms / 29–30 ms |

Абсолютные значения зависят от хоста; важна не разница qps сама по себе, а
отсутствие starvation REST: при отдельном `api`-процессе его p50/p99 не растут
под DNS-нагрузкой и DNS не деградирует из-за REST.
