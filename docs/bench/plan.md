# План бенчмарков и приёмки прототипа M1

- **Область:** `pulse-zonefile` (формат v1), `pulse-runtime` (io_uring), сквозной путь UDP/TCP
- **Статус:** проект, на утверждение
- **Связанные:** `docs/adr/0003-zonefile-format.md` (§2.1 — принятые целевые метрики), `docs/spec/zonefile-v1.md`, `docs/spec/io-uring-runtime.md`, `docs/spec/domain-model.md` (§5.1 — `lookup` p50 ≤ 300 нс, ответ p99 ≤ 2 µs)

---

## 1. Что доказываем на M1

| Гипотеза | Как опровергается |
|---|---|
| Формат даёт zero-copy чтение: зона 15–40 нс, RRset p50 ≤ 500 нс, p99 ≤ 2 µs | микробенчмарк на реалистичной зоне 1M RRset (тёплый кеш) |
| Инкрементальный коммит стоит миллисекунды, а не секунды | коммит 1 RR в зоне 1M RRset |
| Crash safety реальна, а не «на бумаге» | 10⁴ kill -9 + инъекция torn write; сверка счётчика подтверждённых txn |
| Нет утечек страниц/памяти на длинной дистанции | 10⁷ операций, RSS и freelist-баланс |
| Рантайм не блокируется | `strace`/`bpftrace`: нет syscall'ов и аллокаций на hot-path |
| 100k qps достижимы на 8 ядрах (M3) | сквозной нагрузочный тест |
| Формат готов к DNSSEC (без крипто-пайплайна) | golden-тесты канонизации: NSEC-порядок, сортировка RR в RRset, отсутствие компрессии в RDATA |

**Границы M1:**
- один процесс (несколько потоков); межпроцессные читатели — **M3**;
- DNSSEC — только форматная готовность (канонизация); подпись/валидация — **M5**;
- `map_size` фиксирован (дефолт 4 GiB, тесты 64–256 МиБ); рост файла — **не M1** (`MapFull`).

**Вне M1:** DNSSEC-крипто-перф (M5), DoT/DoH (M6), многохостовые сценарии, AXFR-на-гигабайтных зонах (M3), межпроцессные читатели (M3).

## 2. Метрики: определения

| Метрика | Определение | Единица | Как снимается |
|---|---|---|---|
| `qps` | число ответов, отправленных сервером за интервал (не запросов!) | req/s | счётчик сервера `responses_total` / время; сверка с клиентом |
| `drop_rate` | `(sent_by_client − received_by_server) / sent_by_client` | % | счётчики клиента и сервера + `SO_RXQ_OVFL`/`kfree_skb` |
| `latency p50/p99/p999` | время от отправки запроса клиентом до получения ответа, по HDR-гистограмме с ns-разрешением | ns | loadgen (клиентская сторона) |
| `server_latency` | время `handle()` внутри сервера (без сети) | ns | HDR на сервере |
| `cpu_total`, `cpu_per_core` | `%` утилизации | % | `/proc/stat`, `pidstat` |
| `rss` | `VmRSS` процесса | MiB | `/proc/<pid>/status` |
| `pss_file` | вклад mmap-файла зон (shared) | MiB | `smaps_rollup` |
| `page_faults` | minor/major на запрос | шт | `perf stat -e page-faults,minor-faults` |
| `zone_hit_rate` | доля запросов, для которых зона найдена | % | счётчик |
| `rrset_hit_rate` | доля запросов с найденным RRset (без NXDOMAIN/NODATA) | % | счётчик |
| `axfr_throughput` | RR/с и MiB/с при выгрузке зоны | RR/s | тест AXFR-сервера |
| `commit_latency` | `begin→commit` возврат | ns | criterion + HDR |
| `recovery_time` | от `open()` до готовности отдавать ответы | ms | тест |
| `write_amplification` | записанных байт / байт полезной правки | × | счётчик `pwrite`-байт |

Обязательные правила измерения:

1. **Латентность меряет клиент**, а не сервер (иначе сеть и планировщик выпадают).
2. **Дропы считаются**, а не игнорируются: тест с дропами недействителен (кроме сценария «деградация»).
3. **Прогрев** ≥ 10 с или ≥ 1M запросов до начала измерения.
4. **Три прогона**, в отчёт — медиана; указывается разброс.
5. **Пиннинг**: сервер и клиент на разных NUMA-узлах/машинах, `taskset` для ядер, `performance` governor, отключённый turbo фиксируется в отчёте.
6. Гистограммы HDR с точностью 1 µs (для sub-µs — 100 нс), max запоминается отдельно.

## 3. Окружение

| Параметр | Значение |
|---|---|
| CPU | 8 физических ядер (целевой профиль), SMT выключен или учтён |
| RAM | ≥ 32 GiB, `mmap` зоны в page cache |
| Диск | NVMe (fdatasync p50 ≤ 100 µs, p99 ≤ 1 мс) — измеряется `fio` перед тестами |
| Сеть | 10/25 GbE, loopback (`127.0.0.1`) для функциональных, отдельная машина для ≥ 1M qps |
| Ядро | 7.x, `io_uring` L3 |
| Файл зон | `map_size` = 4 GiB по умолчанию (sparse); функциональные тесты — 64–256 МиБ; стабильностный тест 10M RRset — 2 GiB |
| sysctl | по `docs/spec/io-uring-runtime.md` §16 |
| Часы | `CLOCK_MONOTONIC` для латентности, `CLOCK_MONOTONIC_RAW` для сверки |

**Baseline (целевые значения):**

| Показатель | Цель (сквозной профиль, M3) | Источник |
|---|---|---|
| authoritative UDP | 100 000 qps на 8 ядрах | задание |
| p99 latency в LAN | < 1 мс | задание |
| p999 latency | < 5 мс | производная цель |
| RSS при 1M RRset | ≤ 512 MiB (включая mmap в PSS) | производная |
| CPU при 100k qps | ≤ 70% (8 ядер) | запас на всплески |
| AXFR | ≥ 200 000 RR/s | производная |

## 4. Инструменты

| Инструмент | Назначение | Почему он |
|---|---|---|
| `criterion` 0.5 | микробенчмарки (lookup, insert, commit, компаратор, RLE) | статистика, baseline-файлы, регрессии |
| `iai-callgrind` | детерминированные счётчики инструкций/cache-miss | CI без «шумных» секунд, ловит регрессии алгоритма |
| `divan` (опционально) | быстрые parametric-бенчи (размеры зон) | удобные параметризации |
| `dnsperf` 2.14+ | внешняя валидация QPS/latency, доверие сообщества | стандарт индустрии, не наш баг |
| собственный `pulseload` | профили (mix запросов), HDR, дропы, TCP-pipelining, AXFR | dnsperf не умеет наш mix и не даёт нужных счётчиков |
| `perf record -g` + `flamegraph` | CPU-профиль, on-CPU | стандарт |
| `perf stat` | IPC, cache-misses, page-faults, branch-misses | численные цели |
| `bpftrace`/`bcc` | off-CPU, `syscall:sys_enter` счётчики, `vfs_write` | доказательство отсутствия syscall'ов |
| `strace -c -f` | проверка «нет syscall'ов на hot-path» | грубая, но убедительная проверка |
| `heaptrack` / `dhat` | аллокации (должно быть 0 на запрос) | утечки и лишние `malloc` |
| `valgrind --tool=memcheck/helgrind` | UB и гонки в тестах | безопасность |
| `Miri` + `cargo-fuzz` | UB в unsafe-доступе к mmap, парсер формата | SEC-ZF-012 |
| `fio` | калибровка `fdatasync` | обоснование режимов durability |
| `dm-flakey` / `dm-log-writes` | имитация power loss, точное воспроизведение состояния | проверка durability beyond SIGKILL |
| QEMU + `cache=unsafe/writethrough` | «выдернуть питание» | финальная проверка |

Правило: **никаких самодельных таймеров** (`Instant::now()` в цикле) для латентности — только HDR-гистограмма, иначе искажение на 20–50 нс на итерацию.

## 6. Нагрузочные сценарии (сквозные)

### 6.1. Профиль запросов (фиксированный, генерируется из зоны)

| Класс | Доля | Описание |
|---|---|---|
| HIT_A | 55% | существующее имя, тип A/AAAA |
| HIT_OTHER | 15% | существующее имя, прочие типы (MX/TXT/SRV/NS) |

| LARGE | 1% | ответ 1–3 KiB (EDNS, TXT) |

| # | Сценарий | Параметры | Что проверяем |
|---|---|---|---|

| S13 | 24-часовой soak | S1 при 80k qps | RSS (рост ≤ 5%), fd, freelist, утечки |

### 6.3. Собственный `pulseload`

Требования (dnsperf-совместимые флаги):

```
pulseload --server 10.0.0.1:53 --mode udp|tcp --threads 8 --qps 100000 \
          --duration 60 --profile profile.json --edns 1232 --timeout 1s \
          --hdr-out run.hdr --csv-out run.csv
```

- Профиль запросов — JSON, сгенерированный из зонного файла (`zonefile gen-profile`), с сохранением распределения классов §6.1.
- Латентность — `CLOCK_MONOTONIC`, HDR-гистограмма 1 µs (100 нс для микропрофиля), отдельно запоминается max.
- Счётчики: отправлено, получено, таймауты, ошибки, дропы (по `SO_RXQ_OVFL` и ядерному `udpInErrors`).
- Валидация ответов: `ID`/`question` совпадают, `RCODE` ожидаемый (проверка «сервер отвечает правильный SERVFAIL, а не мусор»).
- Идемпотентность прогонов: seeded RNG, один и тот же профиль → одинаковый поток запросов.

Валидация загрузчика: `pulseload` против `dnsperf` на одном и том же сервере должен давать qps в пределах ±3%, иначе — баг загрузчика, а не сервера.

## 7. Критерии приёмки

Разделение по этапам (roadmap: M1 — `pulse-zonefile`, M3 — `pulsed` + транспорт):

- **§7.1 — приёмка M1** (обязательна для закрытия этапа): прототип writer/reader формата v1.
- **§7.2–7.3 — цели M3** (фиксируются сейчас как направление и как baseline для регрессий; проверяются на M3, когда появятся транспорт и сервер).

### 7.1. `pulse-zonefile` (прототип writer/reader) — **M1**

| # | Критерий | Метод проверки | Порог |
|---|---|---|---|
| A1 | Поиск зоны: p50 / p99 | `criterion`, 10k зон | 15–40 нс / ≤ 120 нс |
| A2 | Поиск RRset (1M RRset): p50 / p99 | `criterion`, тёплый page cache | ≤ 500 нс (цель порта: 300 нс) / ≤ 2 µs |
| A3 | Вставка 1 RR + commit: p50 | `criterion`, `Sync`, NVMe | ≤ 2 мс |
| A4 | Вставка 1 RR + commit: p50 | `MODE_NOSYNC` | ≤ 200 µs |
| A5 | Страниц на коммит 1 RR | счётчик `pwrite` | ≤ 8 |
| A6 | Восстановление после `kill -9` | 10⁴ итераций в случайной точке | 0 потерянных подтверждённых коммитов, 0 `Corrupt` |
| A7 | Инъекция частичной записи | `LD_PRELOAD`-шим, обрезающий `pwrite`/`fdatasync` | файл открывается, состояние = последний полный коммит |
| A8 | Утечки за 10⁷ операций | RSS/PSS, `freelist_entries` | RSS +≤ 5%, freelist-баланс точный |
| A9 | Нет утечек страниц | `fsck --verify` после 10⁷ операций | `leaked == 0`, `corrupt == 0` |
| A10 | Отсутствие материализации | профиль под нагрузкой: 0 копий размером с RRset/зону, 0 аллокаций на lookup; для overflow-RDATA — ≤ 1 копия на RR (`copy_into`/`chunks`) | 0 копий набора, 0 аллокаций |
| A11 | Обход 1M RRset (`enumerate`) | `criterion` | ≤ 250 мс, порядок канонический |
| A12 | Компакция 1M | `compact_zone` | ≤ 2 с, размер файла не растёт |
| A13 | Golden-file §22 спеки | тест читает пример байт-в-байт | совпадение |
| A14 | Fuzz/Miri/loom | `cargo-fuzz` 24 ч (**4 таргета**: `zonefile_read/write/roundtrip`, `reader_table_state`), `Miri` на чистой логике, **`loom`/TSan** на `pin`/`unpin` × `oldest_reader_txn`/`reclaim_txn` | нет паник/UB/OOM; инвариант «страница с `free_txn < durable_watermark` **и** `free_txn ≤ oldest_reader_txn` может выдаваться; иначе не выдаётся и не перезаписывается» не нарушается |
| A15 | **Форматная готовность к DNSSEC** (golden-тесты канонизации) | NSEC-порядок = обход `next_name`; RR внутри RRset отсортированы по каноническому RDATA; RDATA без компрессии; lowercase-инвариант; `RRSIG` различаются по `subtype` | совпадение с эталоном RFC 4034 §6.1/§6.3; **подпись не проверяется (M5)** |
| A16 | Поведение при исчерпании карты | файл `map_size` 64 МиБ, заполнить до `page_count_max` | `MapFull` (не паника, не порча), чтение продолжает работать |
| A17 | Отказ при невозможном `mmap` | квота/`RLIMIT`/ФС без sparse | отказ старта `MapAllocFailed` с понятной причиной |
| A18 | Жизненный цикл зоны | create → `Initializing` (REFUSED-состояние) → первый коммит → `Serving`; delete → `Tombstone` (мгновенно невидима); повторный create того же origin | новый `zone_seq`; старый `ZoneId` не «оживает»; `fsck` без утечек после `reclaim_txn` |
| A19 | Per-zone meta-блок | inline-настройки ≤ 4016 Б; upstream-блоб 4096 Б → overflow; `EditOp::SetZoneMeta` в одной транзакции с правкой RRset | чтение `ZoneSettingsRef` O(1) по фиксированным полям; `ZoneMetaTooLarge` при > 256 KiB; kill -9 в момент `SetZoneMeta` не даёт смеси |
| A20 | Два writer'а на одном файле | два процесса открывают writer на один файл | второй получает `Busy` (lock-файл `<zonefile>.lock`); данные не меняются |
| A21 | Усечённый существующий файл | `truncate` готового файла на 1 страницу; открыть writer'ом и читателем | оба получают `TruncatedFile`; `ftruncate` не выполняется, файл не «доращивается» |
| A22 | Внутрипроцессный читатель (M1) | N потоков берут снапшоты, писатель коммитит 10⁴ раз; прогон под **TSan** и в `loom`-модели (pin/unpin × reclaim) | читатели видят только целые снапшоты; `oldest_reader_txn` учитывается; нет переиспользования страниц с `free_txn ≥ durable_watermark` или `free_txn > oldest_reader_txn`; межпроцессный вариант — M3 |

**Область M1:** один процесс, несколько потоков. Межпроцессный доступ (несколько процессов на один файл, отдельный lock-файл writer'а, `LONG_HOLD`) — **критерии M3**, в M1 не тестируется.

### 7.2. `pulse-runtime` — цели M3

| # | Критерий | Метод | Порог |
|---|---|---|---|
| B1 | Нет syscall'ов на hot-path | `strace -c -f` под S1 | syscall'ы только `io_uring_enter`/`epoll_wait` (+ шум старта) |
| B2 | Нет аллокаций на запрос | `dhat`/`heaptrack` под S1 | 0 allocs/query |
| B3 | Нет блокировок | `perf lock`, `bpftrace` | 0 contended locks |
| B4 | Multishot recv работает | счётчик CQE vs отправлено | 1 SQE на сокет, N CQE |
| B5 | Backpressure | S2 до 200k qps | дропы только на клиенте, нет роста p999 > 50× |
| B6 | Эквивалентность epoll | S12 | qps ≥ 70% от uring, ответы идентичны |
| B7 | Устойчивость к slowloris | S8 | RSS ≤ 300 МиБ, соединения закрываются |
| B8 | Таймеры не дрейфуют | тест 10⁶ таймеров, сверка дедлайнов | ошибка ≤ 2 мс |

### 7.3. Сквозной путь — цели M3

| # | Критерий | Метод | Порог |
|---|---|---|---|
| C1 | UDP authoritative | S1 | 100 000 qps, p99 < 1 мс, p999 < 5 мс |
| C2 | CPU при C1 | `pidstat` | ≤ 70% (8 ядер) |
| C3 | RSS при C1 (зона 1M) | `smaps_rollup` | ≤ 512 МиБ |
| C4 | TCP | S6 | ≥ 50 000 qps, p99 < 2 мс |
| C5 | AXFR | S9 | ≥ 200 000 RR/s |
| C6 | Коммиты под нагрузкой | S10 | p99 UDP ≤ 2× от baseline, 0 SERVFAIL |
| C7 | Reload | S11 | пауза ≤ 5 мс, 0 SERVFAIL |
| C8 | Soak 24 ч | S13 | RSS +≤ 5%, fd стабильны, 0 `Corrupt` |

**Границы сквозных критериев:** проверяются на M3; профиль — один процесс сервера, много-процессный (несколько серверов/читателей на один файл, отдельный lock-файл writer'а) — отдельный прогон на M3. DNSSEC-подпись в C1–C8 не входит (M5); форматная готовность проверяется в M1 (A15).

**Правило приёмки:** критерий считается выполненным только при приложенном артефакте (вывод критерия/гистограмма/лог `fsck`/график). «На глаз быстро» — не артефакт.

## 8. Тесты crash safety

### 8.1. `kill -9` в случайной точке

```
for i in 1..10_000:
    start writer-процесс с seed=i
    выполнить K=100..1000 коммитов, каждый пишет "commit N подтверждён" в append-only файл-свидетель (fsync)
    kill -9 в случайный момент (после случайной доли работы)
    открыть файл, fsck --verify
    проверить: txnid(active) >= последний_подтверждённый_txn
    проверить: нет Corrupt, нет нарушений ключей/порядка
```

Дополнительно: сверка, что восстановленное состояние **является** одним из когда-либо закоммиченных (хеш содержимого против журнала коммитов), а не «смесью».

### 8.2. Инъекция частичных записей

`LD_PRELOAD`-шим перехватывает `pwrite`, `pwritev`, `fdatasync`, `fsync` и по seed'у:
- обрезает запись до 1 байта / половины страницы / границы сектора;
- пропускает `fdatasync` (имитация `MODE_NOSYNC`);
- переставляет порядок двух записей (проверка, что нас спасает CRC, а не удача).

Ожидание: либо старый, либо новый снапшот; никогда — повреждение.

### 8.3. Power loss

- `dm-log-writes` поверх тестового раздела, запись «состояния диска» на каждом шаге, затем replay в QEMU с `cache=none` → проверка каждого шага.
- `dm-flakey` с `drop_writes` на случайные окна (проверка CRC-детекта).

### 8.4. Усечение и подмена файла

- `truncate -s 4096` работающего файла → сервер: `SIGBUS`-обработчик аварийно завершает; рестарт: `Corrupt` (SEC-ZF-009).
- `rename`/symlink-swap → `fstat`-проверка отклоняет (SEC-ZF-010).

## 9. Тест стабильности (10⁷ операций)

Окружение: `map_size = 2 GiB` (10M RRset ≈ 900 МиБ по раскладке), один процесс. `MapFull` в этом тесте — провал (карта обязана вмещать профиль).

```
Фаза 1: 10⁷ upsert (случайные ключи, 30% перезапись существующих) в 100 зон по 100k RRset
        - после каждых 10⁶: фиксировать RSS/PSS, page_count_high_water, free_page_count, freelist_entries
        - баланс: high_water - free == достижимые страницы (fsck)
Фаза 2: 10⁶ delete (освобождение половины зоны)
Фаза 3: 10⁶ upsert заново (проверка переиспользования страниц)
Фаза 4: 100 × compact_zone
Фаза 5: финальный fsck --verify
```

Критерии: RSS +≤ 5% между фазой 1 и концом; `leaked == 0`; `corrupt == 0`; число открытых fd постоянно; время каждой фазы не растёт более чем логарифмически.

## 10. Профилирование: рабочий процесс

1. **Criterion-регрессии в CI** (каждый PR): `zone_lookup_hit`, `rrset_lookup_1m`, `upsert_1rr_nosync`, `name_cmp_*`. Порог регрессии — 10% (шум), baseline хранится в репозитории.
2. **`iai-callgrind` в CI** (детерминированно): инструкции и cache-miss для `rrset_lookup_1m`; регрессия > 5% — блокер.
3. **Ночной нагрузочный прогон** (S1, S2, S6) на выделенном стенде: публикация отчёта (qps, p50/p99/p999, CPU, RSS).
4. **`perf record -g --call-graph dwarf`** при провале цели: flamegraph прикладывается к отчёту; смотреть `mmap`-page-fault, `memcpy`, `name_cmp`, `_mm_crc32`.
5. **`perf stat`** для проверки гипотез: IPC < 1 → зависимости по данным; cache-miss > 30% → рабочий набор не влезает в L3 (лечится `compact_zone`/`INLINE_VALUE_MAX`).
6. **`bpftrace`** для off-CPU: `offcputime` на worker'ах; любой off-CPU > 1 мс — баг (кроме `io_uring_enter` ожидания).
7. **`strace -c`** как «тест на блокировки»: падение с 20 syscall/запрос до 2 — цель.

## 12. Риски плана

| Риск | Влияние | Смягчение |
|---|---|---|
| `mmap`-page-fault доминирует в p99 на холодном кеше | ложный провал C1 | прогрев + `MADV_WILLNEED`; отдельный замер «cold» и «warm» |
| Loopback искажает сетевую часть | завышенный qps | сквозные цифры — только с отдельной машины/интерфейсом |
| `io_uring` заблокирован в CI-контейнере | тесты B* не выполняются | CI-раннер с `--security-opt seccomp=unconfined` + маркер «skipped» в отчёте |
| NVMe с непредсказуемым fsync | провал A3 | калибровка `fio` перед прогоном; `Flush`-режим как альтернатива |
| Шум планировщика на 8 ядрах | нестабильные p999 | pinning, `SCHED_FIFO` для клиента, отключение turbo |
| Собственный loadgen ошибается | неверные выводы | кросс-валидация с `dnsperf` ±3% |
| Критерий A2 (500 нс) недостижим при 1M в холодном L3 | срыв M1 | цель сформулирована для тёплого кеша; cold-профиль — отдельная метрика (§5.1, 10M) |
