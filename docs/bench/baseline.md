v2 читает файл через `pread`/`pwrite` (`pulse-zonefile::map` используется только v1), поэтому `mmap RSS` = 0 — это ожидаемо. `PageCache` — `fincore RES` файла зон; `Диск MiB` — фактически занятые блоки (sparse-файл может быть больше). Рост `RssAnon` — heap; рост `PageCache` — прогрев файла, не утечка. Для серий < 60 с «Δ %» включает прогрев и не является вердиктом об утечке; вердикт «стабильно/рост > 5%» выносится только для soak ≥ 60 с.

## Блокер: 1000 зон

Сценарий `1000 зон` воспроизводимо **зависает** в v2-writer'е: процесс создаёт 255 зон и уходит в `__futex_wait` без CPU/прогресса. `fsck` убитого файла: `zones=257`, `ok=true`; последняя зона — 255. Похоже на коллизию lease-шарда: `zone_seq=256` даёт `256 % 256 = 0`, тот же шард, что у каталога (зона 0), и нереентерабельный mutex каталога берётся повторно при `create_zone`.

Воспроизведение: `pulse-zonegen --zones 1000 --rrsets 100` (зависает на ~255 зонах). Работает `--zones 255 --rrsets 392` (100 725 RRset). Поэтому ось «число зон» в baseline — **255**, а не 1000; это дефект production-кода, не харнесса. Исправление вне рамок задачи (production-код не менялся).

## Выводы и узкие места

- UDP 8 worker'ов держит 10k qps без потерь и таймаутов (p99 778.8 µs); запаса по дропам на этой ставке нет смысла искать — поднимайте ставку до насыщения.
- NXDOMAIN на той же ставке 10k: p99 100.9 ms против 778.8 µs у mix-hit (130×). Узкое место — перебор суффиксов/негативный ответ; оптимизация NX-пути даёт наибольший выигрыш по p99 (порядок — единицы/десятки раз), затем уже qps.
- REST под DNS-нагрузкой: 62 PUT/s (цель 80), ошибок 0, p50 117.8 ms / p99 355.3 ms. API-путь чувствителен к CPU-конкуренции с UDP-worker'ами; выносить API на отдельные ядра/процесс или батчить записи.
- Bulk-load 1M RRset: ~6 COW-страниц на RRset, cursor до ~24 GiB, 26 мин и 16 GiB на диске; при импорте 1000 зон writer зависает на zone_seq=256 (см. раздел «Блокер»). Это главный практический дефект, не влияющий на чтение, но блокирующий большие стенды.
- 1M RRset: RSS 36 MiB (anon 29 MiB, file 7 MiB, mmap 0 MiB); бюджет 512 MiB выполнен.
- RssAnon на 1M RRset 29 MiB — это heap/index/кэш, не mmap; рост RssAnon в soak — утечка, рост RssFile/mmap — page cache (норма).
- Soak 10 мин: RSS 54 → 53 MiB (-2.51%), наклон -260.1 KiB/мин → стабильно.
- CPU-hotspots по функциям не сняты: `perf record` заблокирован `kernel.perf_event_paranoid=2` (сэмплирование), хотя `perf stat` считает cycles/instructions. Для flamegraph нужен paranoid 1 или CAP_PERFMON.
- Транспорты: TCP 40139 qps, DoH h2 13965 qps при 8 соединениях; разница — TLS/h2 handshake и HTTP-обработка. Для DoH масштабирование упирается в число соединений/stream'ов клиента, а не в UDP worker'ы.
- `lookup_ref` (zero-copy) — 7.6454 allocs/op, 1223.5 B/op; `lookup` материализует RRset и аллоцирует — на горячем пути предпочтителен `lookup_ref`.
- Loopback + SMT: клиент и сервер делят 8 vCPU; абсолютные qps занижены, p99 завышен. Для приёмки C1 (100k qps) нужен отдельный клиентский хост и отключённый SMT/turbo.

## Воспроизведение

```bash
cargo build --release -p pulsed -p pulse-loadgen
target/release/pulse-bench --out-dir target/bench --report docs/bench/baseline.md --json docs/bench/baseline.json
cargo run -p pulse-loadgen --release --features alloc --bin pulse-alloc -- \
  --data target/bench/z1m.v2 --rrsets 1000000 --ops 20000 --json-out target/bench/alloc.json
cargo bench -p pulsed --bench zone_writes
```
