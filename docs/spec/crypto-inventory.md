# Инвентарь криптографии pulse-dns

- **Статус:** Proposed
- **Область:** v1 (DNSSEC sign+validate, TSIG, TLS/mTLS для REST и репликации, токены API, целостность mmap-файла).
- **Связанные документы:** [Модель угроз](threat-model.md), [ADR-0004](../adr/0004-security-model.md).

Документ отвечает на вопросы: **какая криптография используется**, **где именно**, **какими алгоритмами и параметрами**, **какие крейты допустимы**, **что запрещено** и **как это проверяется**.

---

## 1. Принципы

1. **Никаких собственных реализаций крипто.** Только vetted-крейты с внешним аудитом.
2. **Один основной бэкенд.** `aws-lc-rs` — для TLS, подписей и HMAC. Дублирование бэкендов запрещено без поправки к ADR.
3. **CSPRNG только из ОС.** `getrandom(2)`; никаких seed'ов из времени/PID/`rand`-адаптеров для секретов.
4. **Constant-time** для сравнения секретов, MAC и результатов проверки подписи.
5. **Zeroize** для ключевого материала; секреты не логируются и не попадают в `Debug`/дампы.
6. **Запрет слабых алгоритмов по умолчанию.** MD5/SHA-1 — только legacy-совместимость за feature-флагом с обоснованием.
7. **Крипто-политика проверяема** — тестами (KAT), линтами и `cargo-deny`.

| CR-12 | Целостность mmap | CRC32C на страницу (corruption), BLAKE3-манифест файла | `crc32c`, `blake3` | `pulse-zonefile` | `V:unit`, `V:fuzz` |
| CR-13 | KDF/деривация подключей (если нужно) | HKDF-SHA256 | `aws-lc-rs`/`hkdf` | внутренние нужды | KAT |

## 3. DNSSEC: матрица алгоритмов

Соответствие RFC 8624 и последующим обновлениям. `sign` — подпись зон, `verify` — валидация.

| Alg | Название | sign | verify | Статус в pulse-dns |
|---|---|---|---|---|
| 1 | RSAMD5 | ✗ | ✗ | запрещён |
| 3 | DSA/SHA-1 | ✗ | ✗ | запрещён |
| 5 | RSASHA1 | ✗ | △ opt-in | только legacy-валидация за флагом |
| 6 | DSA-NSEC3-SHA1 | ✗ | ✗ | запрещён |
| 7 | RSASHA1-NSEC3-SHA1 | ✗ | △ opt-in | только legacy-валидация за флагом |
| 8 | RSASHA256 | ✓ (обязателен для совместимости) | ✓ | поддерживается |
| 10 | RSASHA512 | ○ | ✓ | валидация обязательна, подпись опциональна |
| 12 | ECC-GOST | ✗ | ✗ | не поддерживается |
| 13 | ECDSAP256SHA256 | ✓ (по умолчанию) | ✓ | основной |
| 14 | ECDSAP384SHA384 | ○ | ✓ | валидация, подпись опциональна |
| 15 | ED25519 | ✓ (рекомендуется) | ✓ | поддерживается |
| 16 | ED448 | ○ (optional) | ○ (optional) | по возможности, не обязателен |
| 253/254 | private | ✗ | ✗ | не поддерживается |

Обозначения: ✓ обязательно, ○ опционально, △ только legacy opt-in, ✗ запрещено.

**Правила:**
- RSA/SHA-256 (alg 8) **обязателен** для совместимости; для новых ключей дефолт — ECDSA P-256 (13), рекомендуется Ed25519 (15).
- Подпись SHA-1 (5/7) технически невозможна — код возвращает ошибку `UnsupportedAlgorithm`, покрыто тестом.
- Понижение алгоритма (downgrade) запрещено: набор допустимых алгоритмов задаётся конфигом и проверяется при валидации.
- При валидации алгоритм, отсутствующий в allowlist, даёт `bogus` → SERVFAIL, а не `insecure`.

### NSEC/NSEC3

- NSEC3 iterations = **0** (RFC 9276); salt — минимум 8 байт или пустой по политике.
- NSEC3 opt-out — только осознанно, с предупреждением при генерации.
- Число NSEC3-хешей и итераций ограничено (защита от DoS, см. KeyTrap).

## 4. TSIG

| Параметр | Значение |
|---|---|
| Алгоритм по умолчанию | `hmac-sha256` |
| Допустимые | `hmac-sha256`, `hmac-sha512` |
| Legacy (opt-in) | `hmac-sha1`, `hmac-md5` — только per-key флаг `allow_legacy_hmac_md5 = true` (по умолчанию выключен); при использовании — warning в лог и метрика; deprecated, удаление — v1.1 |
| Fudge | 300 с |
| Сравнение MAC | constant-time (`subtle`) |
| Replay | проверка времени + MAC; окно fudge; монотонность не требуется протоколом, но аномалии логируются |
| Хранение ключа | файл `0600`, каталог `0700`, `zeroize` |
| Имя ключа | не секрет, может быть в логах |

Референсы: RFC 8945 (TSIG), RFC 5936 (AXFR), RFC 1995 (IXFR), RFC 1996 (NOTIFY).

## 5. TLS / mTLS

| Параметр | Значение |
|---|---|
| Библиотека | `rustls` (без OpenSSL/native-tls) |
| Версии | TLS 1.3 (приоритет), TLS 1.2 (совместимость) |
| Сьюты | только AEAD: `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`; для 1.2 — ECDHE + AEAD |
| Группы | X25519, P-256 |
| Renegotiation | запрещён |
| Валидация сертификата | полная цепочка, hostname; корни — `webpki-roots` по умолчанию, опция системных (`rustls-native-certs`); лицензии обеих зависимостей проверяются в `cargo-deny` |
| mTLS | клиентский сертификат для репликации/админ-эндпоинтов; pinning опционален |
| Приватный ключ TLS | `0600`, `zeroize`, без пароля в argv |

Правило: TLS обязателен для любого не-loopback интерфейса (SEC-API-001, SEC-CR-009).

## 6. Случайность

| Применение | Источник | Требования |
|---|---|---|
| TXID DNS | `getrandom` | 16 бит на запрос, уникальность в in-flight |
| Source port | `getrandom` (диапазон ephemeral) | на запрос, уникальность tuple |
| API-токены | `getrandom` | 32 байта |
| DNSSEC nonce/ключи | `getrandom` / vetted-крипто | без предсказуемости |
| Cookie-секрет | `getrandom` при старте | ротация по политике |
| Соль NSEC3 | `getrandom` | ≥ 8 байт |

Запрещено: `rand::thread_rng()` и любые PRNG для **секретов**; время/PID как seed; переиспользование nonce.

`getrandom` на раннем старте может блокироваться — используется `GRND_NONBLOCK` с явной ошибкой «недостаточно энтропии» вместо тихого fallback.

## 7. Управление ключами

### 7.1. Хранение

- Отдельный каталог `0700`; файлы приватных ключей `0600`; владелец — `pulse-dns`.
- Ключ загружается только в память: `Zeroizing<...>`, `#[derive(ZeroizeOnDrop)]`; `zeroize` при выгрузке; `mlock` (SEC-OPS-006).
- **Никогда:** логи, `Debug`, `argv`, world-readable конфиг, plaintext-экспорт через API (SEC-API-013).
- Аудит-лог операций с ключами: генерация, загрузка/выгрузка, ротация, экспорт (SEC-CR-003).
- HSM/PKCS#11 (`cryptoki`) — **не в v1**, roadmap; при появлении приватный ключ не покидает токен.

### 7.2. Ротация

- KSK/ZSK: pre-publish → double-sign → retire (RFC 6781, RFC 7583).
- Автоматические инварианты: зона не остаётся без валидной подписи; старый ключ не удаляется, пока есть зависимые RRSIG.
- Каждая смена — аудит-событие (SEC-API-007).
- Аварийная ротация при подозрении на компрометацию: отдельный сценарий с оповещением.

### 7.3. Trust anchors

- **Встроенный IANA root KSK в поставке**, обновляется с релизами ПО (не «на лету»).
- Владелец — команда проекта; периодичность — каждый релиз + CI-проверка наличия anchor и срока действия.
- RFC 5011 (автоматическое обновление) — v1.1, с логированием и аудитом.
- Провал проверки не должен отключать валидацию молча — только алерт/блокирующий CI.

## 9. Запрещено

| Запрет | Причина | Как ловим |
|---|---|---|
| Собственная реализация крипто (AES, ECDSA, HMAC, KDF) | Высокий риск ошибок/тайминг-атак | `V:manual` review, `cargo-deny` bans |
| `openssl`, `native-tls` | Тяжёлая C-зависимость, сложнее аудит/сборка | `V:ci` (`cargo-deny` ban) |
| Дублирование крипто-бэкендов (`ring` + `aws-lc-rs`) | Несогласованная политика | `V:ci` ban, `V:manual` |
| MD5 | Криптостойкость сломана | запрещён; исключение — `hmac-md5` TSIG только per-key флагом (default off, deprecated) |
| SHA-1 | Коллизии | запрещён для подписи; legacy-валидация DNSSEC/TSIG — opt-in |
| RSA < 2048, DH < 2048 | Слабая стойкость | `V:cfg` при импорте ключа |
| ECB, статический IV/nonce | Утечка/повтор | нет API; `V:manual` |
| Non-AEAD TLS-сьюты, CBC | Padding-oracle | политика `V:unit` |
| `rand`/`thread_rng` для секретов | Непрозрачность источника | `V:manual`, `V:lint` (обёртка) |
| Сравнение секретов через `==` | Timing-атака | `V:lint` (newtype без `PartialEq`), `V:manual` |
| Plaintext-хранение токенов/ключей | Утечка | `V:integ`, `V:manual` |
| Hardcoded ключи/секреты в коде | Утечка | `V:ci` (secret-scan), `V:manual` |
| Nonce/IV повтор в AEAD/ECDSA | Катастрофическая потеря ключа | vetted-крипто, `V:manual` |

## 10. Проверяемость крипто-политики

| Механизм | Что проверяет |
|---|---|
| KAT-тесты (known-answer) | Соответствие реализаций стандартам (DNSSEC RFC 4034/5702, TSIG RFC 8945, TLS). |
| Матрица алгоритмов (`V:unit`) | Что запрещённые алгоритмы отвергаются, разрешённые — работают. |
| Интероп-тесты (`V:integ`) | Зоны проходят `ldns-verify-zone`/`delv`; TSIG совместим с BIND/Knot. |
| `cargo-deny` (`V:ci`) | Запрещённые крейты/лицензии/источники, advisories. |
| `cargo-audit` (`V:ci`) | Известные уязвимости зависимостей. |
| Fuzz парсинга ключей/сертификатов (`V:fuzz`) | Устойчивость к битым ключам/цепочкам. |
| Miri (`V:miri`) | Отсутствие UB в обёртках над крипто (где применимо). |
| Аудит (`V:manual`) | Отсутствие самописной крипто, корректность SAFETY, zeroize-пути. |
| Secret-scan (`V:ci`) | Нет ключей/токенов в репозитории. |

## 11. Пост-квантовые соображения (roadmap)

- DNSSEC: следить за PQC-алгоритмами для DNSSEC (IANA-регистрации); v1 не поддерживает.
- TLS: гибридный X25519MLKEM768 в `rustls`/`aws-lc-rs` — включить, когда станет стабильным и аудированным.
- Долгосрочная конфиденциальность: ключи DNSSEC — не для шифрования, PQC-риск ниже; TLS-сессии — короткоживущие.
- Решение о PQC — отдельным ADR, не в v1.

## 12. Открытые вопросы

**Все вопросы закрыты:** RSA/SHA-256 (alg 8) обязателен; Ed448 (alg 16) — optional; HSM/PKCS#11 — не в v1 (roadmap); пароли людей не требуются (только bearer-токены); hmac-md5 — только per-key флаг `allow_legacy_hmac_md5`, deprecated, удаление v1.1; trust anchors — встроенный IANA KSK, обновление с релизами, CI-проверка, RFC 5011 в v1.1; TLS-корни — `webpki-roots` по умолчанию, опция системных; DNSCrypt — отдельный ADR + расширение инвентаря в M5.

**Открытых вопросов нет.**
