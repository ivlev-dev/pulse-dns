# ADR 0005. Параллельная запись в один файл: деревья и корни на зону

- **Статус:** предложено (на утверждение Оркестратором); гейт — `docs/adr/0006-parallel-writers-safety.md` §12 (C-1…C-12)
- **Дата:** 2026-11-24
- **Этап:** M1 (формат, один процесс, N потоков) / M3 (межпроцессные писатели, SEC-PW-009)
- **Роль-владелец:** Архитектор ПО (решения, границы, обоснование). Поле-в-поле раскладка и пошаговые протоколы — `docs/spec/parallel-writes-v2.md`; требования безопасности — `docs/adr/0004-security-model.md` §1.1/§1.3 и ADR-0006
- **Связанные:** `docs/adr/0003-zonefile-format.md`, `docs/spec/zonefile-v1.md` §25 (дельта), `docs/spec/domain-model.md` §5.1–5.2, `docs/api/rest-v1.md` §5, `docs/spec/io-uring-runtime.md` §2.1
- **Вытесняет:** глобальную meta, глобальный `txnid`/`durable_txn`/`reclaim_txn`, глобальный freelist, глобальный `oldest_reader_txn`. Страницы, ключи, RLE, overflow, `ZoneMeta`-блок, CRC, `ZoneState`-семантика и структура двухфазного пина сохраняются

Соглашения: `PW-I*`, `PW-C*`, `PW-L*`, `SEC-PW-*` — из ADR-0006 / ADR-0004 §1.3 (источник истины, не дублируются); `A-*` — инварианты этого ADR (уточняют `PW-I*`); `D-A…D-D` — заявленные отклонения от буквы ADR-0006 с доказательством эквивалентности (§10.3); `F2-*` — точки отказа v2 с маппингом на `PW-C*`. Числа производительности помечены «оценка».

## 0. Резюме решения

| # | Решение | Следствие |
|---|---|---|
| 1 | Дерево на зону уже есть в v1; **публикация корня — per-zone**: ring 4 версии × 2 копии в разных A/B-страницах + **chain как safety valve**; запись корня 64 Б | коммит зоны не трогает общие страницы; torn-сектор не убивает обе копии; AXFR-пин не останавливает запись зоны |
| 2 | **Один writer на зону** (lease); разные зоны — параллельно | `Busy` только по своей зоне; кросс-зонных блокировок нет |
| 3 | **Глобальный монотонный `txn`** и `page_limit` (CAS-резервирование батчами). `version(zone)` = `txn` коммита зоны | кросс-зонный ABA закрыт; `page.txn ≤ snapshot` работает только вместе с `owner_zone` |
| 4 | **`owner_zone`** в `PageHeader.reserved1` (+12) под required-флагом | читатель отвергает чужую страницу (`Corrupt`), а не «читает что попало» |
| 5 | **Аллокатор**: курсор/`txn`-билет — `AtomicU64` в памяти (батчи), durable-барьер — `ALLOC_RECORD` (2 копии в разных страницах) + per-zone free pools; bump-first до 85 % | нет глобального freelist; третий writable-регион не нужен; реюз только после durable drop |
| 6 | **Двухфазный group commit**: `ALLOC_RECORD` → `fdatasync` → корни → `fdatasync` → публикация → ack. Два fsync на пачку | латентность = латентность пачки; один fsync на группу запрещён (D-1) |
| 7 | **Каталог = идентичность** (`origin`, `zone_seq`, `kind`, `head_slot`); всё мутируемое — в 64-байтовой записи корня | `create_zone` пишет каталог (редко); `delete_zone` пишет только корень |
| 8 | **Пины**: `EPOCH` (широкий) и `ZONE` (6 пар × u64), двухфазный seqlock + `fence(SeqCst)`; GC считает `MP(z)`/`RV_z`, writers не сканируют таблицу | чтение не блокирует запись; ARM64-корректность; горизонт `txn` — u64 |
| 9 | **Атомарности между зонами нет** (PW-L1). Кросс-зонный срез — `freeze()` (quiesce + fsync) | DNS-операции зоно-локальны; цена — нет мгновенного среза |
| 10 | Формат **v2.0**; v1 — read-only + offline конвертер; даунгрейда нет | миграция без потери данных |
| 11 | **`Snapshot` ceiling = ∞** (зона всегда читается в последней опубликованной версии); согласованный срез — `freeze()` | нет `NoZoneVersion` под нагрузкой; retention только через явный `freeze()` |

Ключевая честная мысль: **параллелизм снимает сериализацию CPU и блокировок, но не потолок `fsync`.** Один файл — один inode; `fdatasync` синхронизирует inode целиком, поэтому throughput записи упирается в «два fsync на пачку». Что покупается: изоляция медленных операций (компакция 5M RRset больше не останавливает запись во все зоны), линейный рост CPU-ёмкости кодирования/CRC до ~4–6 ядер и предсказуемый p99 при параллельных правках разных зон.

## 1. Контекст

### 1.1. Что уже есть в v1

| Компонент | Пригодность для v2 |
|---|---|
| pager, `PageHeader` 40 Б, CRC32C | переиспользуется; `reserved1` (+12) → `owner_zone` |
| superblock A/B, `sync_mode`, `page_size`, секции | переиспользуется; `version_major = 2` |
| COW B+tree, RLE, overflow | переиспользуется постранично |
| reader table, двухфазный пин | структура сохраняется; слот 128 Б, пины зон |
| recovery / torn / `NEEDS_FSCK` | логика сохраняется; объекты — ring корней + `ALLOC_RECORD` |
| lock-файл | M1: `LOCK_EX` на процесс; M3: писатели `LOCK_SH`, recovery/`fsck` `LOCK_EX` (SEC-PW-009) |
| глобальная meta, `txnid`/`durable_txn`/`reclaim_txn`, freelist | **заменяются** (§8) |

Ключевое наблюдение: **«дерево на зону» — не новое требование, а факт v1** (`ZoneEntry.tree_root`). Проблема v1 — единственная точка публикации: любой коммит пишет глобальную meta, а глобальные `txnid`/freelist/`oldest_reader_txn` связывают зоны.

### 1.2. Новое требование

1. Один файл, `mmap`, zero-copy чтение, MVCC-читатели, crash-safety.
2. **Полностью параллельная запись по зонам**: `N` writer-потоков одновременно коммитят разные зоны.
3. **Lock-free аллокация страниц** (без глобального мьютекса/freelist-спина).
4. Commit-протокол и crash-safety — на усмотрение архитектора (направление Оркестратора проверяется в §2).

### 1.3. Проверяемые требования

| ID | Требование | Проверка |
|---|---|---|
| PR-1 | Коммиты в разные зоны не имеют общих точек сериализации, кроме аллокатора, `txn`-билета и пачки | `V:loom` (`root_publish`, `epoch_min`), `V:prop` |
| PR-2 | Коммит в одну зону при параллельном коммите в другую не увеличивает p99 первой > 10 % (оценка) | `V:bench` `commit_p99_parallel_zones` |
| PR-3 | `compact_zone` 5M RRset не блокирует запись в другие зоны | `V:bench` |
| PR-4 | Crash-safety равна `PW-C1..PW-C24`: зона на `V` или `V-1`; «полу-записи» нет | `V:crash` (`kill -9`, `dm-log-writes`, `dm-flakey`), `fsck --verify` |
| PR-5 | Zero-copy: срез `mmap` живёт, пока жив `ZoneSnapshot` | `V:integ`, `V:prop` |
| PR-6 | Throughput ограничен `fsync`, а не блокировками | `V:bench`; профиль ожиданий |
| PR-7 | `fsck` восстанавливает `PW-I3`/`PW-I3a` и возвращает утёкшие страницы | `V:prop`, `V:fsck` |
| PR-8 | API не меняется для одиночного клиента; параллельные правки разных зон не мешают | `V:integ` |
| PR-9 | ARM64: нет use-after-reuse из-за store→load | `V:loom`, ARM64 CI |

### 1.4. Инварианты (уточнение `PW-I1..PW-I10`)

| ID | Инвариант |
|---|---|
| A-1 | Один файл; данные — `PROT_READ`, запись — `pwritev`; writable-регион ровно один — reader table (SEC-ZF-014) |
| A-2 | Зона `Z` имеет ровно одного writer (lease); коммиты `Z` упорядочены по `version` |
| A-3 | `txn` строго возрастает глобально; `version(Z)` = `txn` коммита `Z`; `txn` не переиспользуется после recovery |
| A-4 | Страница, достижимая из выбранной версии `V`, не изменяется и не переиспользуется, пока `V` может быть выбрана recovery или удерживается пином |
| A-5 | Запись корня валидируется целиком (CRC, `owner_zone`, `version`, `root_page`, `page_limit_at_commit`, поля зоны) и выбирается детерминированно (`max version ≤ ceiling`, tie-break A) |
| A-6 | Каждая версия пишется **двумя** копиями в **разных** страницах (A/B-регионы); группы версий `≥ MP(z)` или `≥ D_z` не перезаписываются; при исчерпании ring версия уходит в chain; `ZoneWriterStalled` — только патология |
| A-7 | `max_page_id(V) < page_limit_at_commit(V) ≤ DP` для любой валидной записи; `DP`/`DT` не убывают |
| A-8 | Множества страниц разных зон не пересекаются; `PageHeader.owner_zone` опубликованной страницы зоны `Z` = `Z` |
| A-9 | Страница, выброшенная в версии `F` зоны `Z`, выдаётся только при `F ≥ 2` ∧ `F < D_z` ∧ `F ≤ RV_z` ∧ `F < current_version(Z)`; достижимость bucket'а из durable-записи `V` обеспечена порядком F-10 (`free_head` в `V`, bucket — фаза 1) |
| A-10 | Никогда не опубликованные страницы переиспользуются немедленно (recovery их не видит) |
| A-11 | `Tombstone` невидим `find_zone`/`zones` с публикации; страницы и запись корня освобождаются только при `deleted_txn ≤ RV_z` ∧ `< D_z` |
| A-12 | Ни один writer не сканирует reader table на пути коммита; `MP(z)`/`RV_z` обновляет GC |
| A-13 | Только `x86_64`/`aarch64`, выровненные `AtomicU64`; публикация — `Release`/`Acquire`; пин — `fence(SeqCst)`; `Relaxed` для публикации запрещён |

### 1.5. Не-цели

Параллельная запись **внутри** зоны (шардирование дерева, §2.B); согласованный кросс-зонный срез на hot-path; онлайн-рост `map_size`/`page_size`; распределённая запись; межпроцессная запись до ADR M3.

## 2. Альтернативы

### A. Деревья на зону + история корней на зону (направление Оркестратора, уточнённое)

- **+** Прямое следствие структуры v1: переписывать дерево не нужно, меняется точка публикации и учёт страниц.
- **+** Нет общих страниц/фреймлиста/meta-слота: коммиты зон не пересекаются.
- **+** Медленная операция над зоной изолирована.
- **+** Crash-safety — та же схема «COW + копии записи + CRC + порядок данные→корень».
- **−** Нет согласованного кросс-зонного среза (PW-L1).
- **−** `fsck`/recovery обрабатывают `Z` ring'ов; O(Z) на открытии (уже O(Z) из-за `ZoneIndex`).
- **−** Per-zone пулы: зона, сжавшаяся вдвое, не отдаёт место другим без двухфазной donation (PW-L3).
- **−** Координатор group commit — поток и состояние.

**Вердикт:** принято. «Двойной слот» из направления заменён на **ring 4 версий × 2 копии в разных страницах** — по требованию ADR-0006 (D-3): иначе один застрявший читатель блокирует коммиты зоны, а torn-сектор может убить обе копии.

### B. Шардированный лес внутри зоны

- **+** Единственный способ параллелить запись в одну гигантскую зону (10M RRset, IXFR-in).
- **+** Форматно совместим с A: запись корня указывает на директорию шардов.
- **−** Маршрутизация по диапазону на каждом lookup (+1–2 сравнения), выигрыша в cache miss нет.
- **−** `enumerate`/AXFR/NSEC обязаны мержить шарды: кросс-шардовый курсор, проверка порядка; `next_name` — не один спуск.
- **−** Split/merge на границе шарда — ребалансировка, т.е. распределённая транзакция внутри файла.
- **−** Подпись DNSSEC и `MAX_CUT_SUBTREE_RECORDS`-перестройки затрагивают несколько шардов.
- **−** 99 % зон < 1M RRset, где один writer не узкое место.

**Вердикт:** отклонено для v2.0, зарезервировано (`root.flags.SHARDED` + `shard_count` в минорной версии). Параллелизм **сборки** одной зоны возможен и без шардов: bulk import строит страницы параллельно и публикует одним коммитом.

### C. Append-only лог + per-zone индекс + компакция

- **+** Дешёвый коммит (append + 1 fsync), нет аллокации страниц и COW-пути; идеальный паттерн для NVMe.
- **−** Чтение требует индекса: в памяти — файл не самодостаточен (старт O(лога)); на диске — B+tree поверх лога (+лишний cache miss).
- **−** Zero-copy достижим, но ответ требует косвенности: индекс → запись; p50 300–500 нс только с горячим индексом.
- **−** Компакция = полная перезапись зоны; окно ~2× места; читатели держат старые сегменты.
- **−** `enumerate`/NSEC требуют упорядоченного индекса — фактически того же B+tree.

**Вердикт:** отклонено как основная модель. C показывает главный рычаг: **throughput определяется числом fsync**; поэтому минимизируем fsync (group commit) и оставляем WAL следующим шагом (§4.5).

### D. Одно дерево на файл + page-level latches

- **+** Нет проблемы кросс-зонного среза; параллельная запись внутри зоны.
- **−** Ломает MVCC без блокировок: читатель либо берёт latch, либо не защищён → пропадает zero-copy и p50-цель.
- **−** Ломает crash-safety без WAL: частичная запись страницы на месте видна читателю.
- **−** Латчи верхних уровней — глобальная конкуренция при 50k зон.
- **−** Долгая компакция зоны невозможна без остановки всего дерева.

**Вердикт:** отклонено — несовместимо с «crash-safety + MVCC + zero-copy без WAL».

### Сводка

| Критерий | A (принято) | B | C | D |
|---|---|---|---|---|
| Параллельная запись по зонам | да | да | да | да |
| Запись внутри зоны | нет | да | нет | да |
| Zero-copy без блокировок | да | да (дороже) | да (косвенность) | **нет** |
| Crash-safety без WAL | да | да | да | **нет** |
| Кросс-зонный срез | **нет** | нет | нет | да |
| Новая сущность | ring + координатор | шарды + ребалансировка | лог + индекс + компактор | латчи + WAL |
| Ниша | v2.0 | гигантская зона | очень высокий write-rate | OLTP |

«Файл на зону» отклонено ещё в ADR 0003 (§3.E): тысячи `mmap`/`fsync`, нет единого `fsck`/`instance_uuid`, несовместимо с «один файл».

## 3. Решение

### 3.1. Разделение документов

| Документ | Что фиксирует | Не дублирует |
|---|---|---|
| этот ADR | решения, границы, модель конкурентности, цена, миграция, отклонения | раскладку полей |
| `docs/spec/parallel-writes-v2.md` | точные структуры, смещения, пошаговые протоколы, лимиты, матрица | обоснование выбора |
| `docs/spec/zonefile-v1.md` §25 | дельту к v1: что вытесняется, семантика, инварианты, совместимость | детали v2 |
| `docs/adr/0006-*` | `PW-I*`, `PW-C*`, `SEC-PW-*` | реализацию |

Одна нормативная раскладка полей на проект — это ограничение введено сознательно: две раскладки неизбежно расходятся.

### 3.2. Публикация корня: ring 4 × 2 в разных страницах

**Запись корня — 64 Б:** `crc32c`, `owner_zone`, `version`, `root_page`, `page_limit_at_commit`, `prev_record` (штатная chain-ссылка), `meta_root`, `ixfr_root`, `tree_level`, `state`, `flags`, `deleted_txn`, `rrset_count`, `soa_serial`, `free_head`. Точные смещения — `parallel-writes-v2` §4.1.

64 Б (а не 32) — потому что `zones()`/`find_zone`/`/serial` должны отдавать `soa_serial`/`state` без второй страницы на зону; в противном случае список 50k зон = 50k случайных чтений.

**Ring.** На зону — 4 версии; каждая версия пишется **двумя** копиями, и копии лежат в **разных 4-KiB страницах** (A-регион и B-регион), чтобы torn-сектор устройства не уничтожил обе. Раскладка: 16 зон на страницу-копию, 512 Б на зону суммарно (25.6 МиБ на 50k зон; ёмкость задаётся `max_zones` при создании).

**Правила перезаписи:**

1. Новая версия `V` пишется в группу `V mod 4`, обе копии (A и B), одним `pwritev`.
2. Группа перезаписывается только при `group.version < MP(z)` ∧ `< D_z` ∧ `< V`; иначе версия уходит в **chain** (см. ниже) — писатель не блокируется. Если мешает только `D_z` (пинов нет), сначала выполняется auto-promotion в `Sync` (§5.2), chain — fallback. `ZoneWriterStalled { zone }` — только если chain не удалось продолжить (исчерпан `MAX_ROOT_CHAIN_PAGES`/нет страницы/I/O).
3. Новейшая версия не затирается текущим коммитом (`group.version < V`).
4. Torn одной копии → валидна вторая (потерь нет); torn обеих копий новейшей → откат ≤ 1 версии (предыдущая группа цела), зона читаема.
5. Все группы биты → `Corrupt(BadZoneHead)` **по зоне**; файл продолжает работать; `fsck --repair --zone`.

**Chain корней** (`PAGE_TYPE_ROOT_CHAIN = 11`) **входит в v2.0** (решение Оркестратора, закрывает F-8 ADR-0006). При исчерпании ring (все 4 группы `≥ MP(z)`/`≥ D_z`) новая версия пишется в append-only chain-страницу: одна запись на страницу, `prev_record` → предыдущая; писатель **не блокируется**. Обход при чтении: ring → chain до `MAX_ROOT_CHAIN_HOPS = 4096`; битая/мусорная запись пропускается по `prev_record`; цикл/превышение глубины → `Corrupt`. `ZoneWriterStalled { zone }` остаётся только для патологии: исчерпан `MAX_ROOT_CHAIN_PAGES = 4096` (16 МиБ/зона), нет страницы под запись или ошибка I/O. Это не противоречит «писатель не блокируется»: **читатель не блокирует писателя** (ring → chain), но у safety valve есть конечная ёмкость; её исчерпание означает «живой застрявший читатель дольше ~4096 коммитов или утечка пина», диагностируется `pw_root_chain_depth{zone}`/`pw_zone_writer_stalled_total{zone}` и лечится оператором (отпустить читателя) или `fsck`. Ротация chain с вытеснением старых записей и `StaleRoot` для читателя — кандидат v2.1, в v2.0 её нет. Стоимость chain — 4 КиБ на версию, только в режиме застрявшего читателя.

### 3.3. Каталог зон = идентичность

`ZoneEntry` v2 (24 Б): `zone_seq`, `kind_flags`, `created_ns`, `head_slot`, `reserved`. Мутируемых полей нет: любой коммит зоны пишет только запись корня.

- `create_zone` = каталог-коммит (единственный писатель каталога) + `head_slot` + первичный корень.
- `delete_zone` = **только** запись корня (`state = Tombstone`, `deleted_txn`). Каталог не пишется; tombstone виден мгновенно; GC удалит каталог-запись и вернёт `head_slot` позже.
- Повторное создание origin — новая каталог-запись (новый `zone_seq`); старая доживает до GC.

### 3.4. `txn`, `page_limit`, `D_z`, `MP(z)`, `RV_z`

| Величина | Смысл |
|---|---|
| `txn` | глобальный монотонный номер коммита (CAS `reserve_txn`, батч) |
| `version(Z)` | `txn` коммита зоны — **не** отдельный счётчик |
| `DP`/`DT` | durable `page_limit`/`txn_limit` из `ALLOC_RECORD` |
| `D_z` | max версия, чей корень подтверждён fsync |
| `MP(z)` | минимум пинов зоны (∞ = нет пинов) |
| `RV_z` | `min(D_z − 1, MP(z), freeze_epoch)`; гейт выдачи страниц |
| `SnapshotId` | `txn` на момент `snapshot()`; **только** каталог/аудит/диагностика, не ceiling |
| `freeze_epoch` | `0` = нет `freeze()`, иначе EPOCH-барьер удержания (входит в `RV_z`) |
| `zone_guard[z]` | seqlock-счётчик зоны (чётный = стабильно) |

**Ceiling снапшота = ∞** (решение Оркестратора, закрывает F-9 ADR-0006). `snapshot()` фиксирует `SnapshotId` и каталог, но **не** ограничивает версию зоны: `zone_snapshot(zone)` выбирает **последнюю опубликованную** версию на момент разрешения, пинит её и валидирует seqlock. Это убирает `NoZoneVersion`/`StaleRoot` под нагрузкой и не требует, чтобы `Snapshot` был retention-барьером для всех зон. Согласованный срез — только `freeze()` (§7): `FreezeGuard` ставит EPOCH-пин на `published_txn` и публикует `freeze_epoch`; запись не блокируется, но рекламация ограничена.

`StaleRoot` остаётся для двух случаев: (а) `select` не нашёл валидной версии вовсе (ring+chain биты/исчерпаны) — фактически порча; (б) зона пересоздана и её версии начались заново. Оба — не штатная нагрузка; retryable после нового `snapshot()`/`fsck`.

### 3.5. Аллокатор

- `reserve_cursor` и `reserve_txn` — `AtomicU64` **в памяти процесса**; `alloc(n)` — CAS батчами (`ALLOC_EXTENT_PAGES = 16`, локальный кэш `ALLOC_THREAD_CACHE_PAGES = 64`, ~0.02 CAS/коммит). `pwrite` по ним не выполняется; writable-регион остаётся один (SEC-ZF-014 сохраняется).
- **`ALLOC_RECORD`** (2 копии в **разных** страницах): `seq`, `page_limit`, `txn_limit`, `leader_term`, `epoch_hint`, CRC. Durable **до** любых корней; запись — часть фазы 1.
- **Публикация**, а не `alloc`, ограничена durable-границей: корень пишется только при `DP > max_allocated_id` и `DT ≥ V`.
- `hard_limit = page_count_max − GC_RESERVE_PAGES`; `GC_RESERVE_PAGES`/`ROOT_RESERVE_PAGES` не выдаются обычным коммитам — иначе GC не сможет опубликовать корень при полном файле (PW-I9).
- Bump-first, пока `DP / page_count_max < 0.85`; затем eligible-страницы своего пула, затем donation.
- Recovery: `DP = max(ALLOC_RECORD.page_limit, cursor, max root.page_limit_at_commit, max pool.page_id+1, page_data_first)`; `DT = max(...)`; `reserve_txn = max(DT, max version) + 1` (обход деревьев на старте запрещён; `max page.txn` проверяет и поднимает `fsck --verify`). Понижение → `AllocWatermarkRegression` → `NEEDS_FSCK` + read-only. `page_data_first` обязателен: иначе на пустом файле `DP` может оказаться ниже начала data-региона.

### 3.6. Пины

Слот 128 Б: `owner_token`, `epoch` (`kind=EPOCH`), `n_pins` (0..6), `kind`, `flags`, `heartbeat_ns`, `pins[6]` = `{zone_seq u32, pad u32, version u64}` (16 Б; `version` на смещении +8 — 8-выровнена; 96 Б). Версия — полный `u64`.

Протокол: `e0 = published` (Acquire) **до** чтения записи корня (барьер против «голова уже перезаписана») → `pin` последней версии (Release) → `fence(SeqCst)` → `zone_guard` дважды (чётный, равный) → `e2 == e0` → версия та же. Ceiling из `SnapshotId` **не** применяется. `> MAX_PINNED_ZONES_PER_SNAPSHOT (64)` зон → EPOCH-пин (`PIN_OVERFLOW`, консервативно). Живой читатель не вытесняется никогда (SEC-ZF-007).

**Исчерпание `PIN_ATTEMPTS = 8` (F-11):** причины различаются, и это разные ошибки.

| Причина 8 отказов | Ошибка | Действие |
|---|---|---|
| `zone_guard[z]` нечётный/меняющийся (застрявший guard, panic без `Drop`, баг) | `ZoneDegraded { zone, epoch }` | зона → read-only + `NEEDS_FSCK`, `pw_zone_degraded_total`, алерт; **другие зоны работают**. Не спин и не retryable в том же вызове |
| `e2 ≠ e0` / версия сменилась (churn публикаций, читатель «не успевает») | `ReaderContended` | retryable: backoff 10 µs, повтор; батч может пере-взять `zone_snapshot` |

`zone_guard` меняется только через RAII `EpochGuard` (odd при входе, even в `Drop`, включая `Abort`/`Io`/`panic=unwind`); «ручной» инкремент запрещён. Требуется `V:loom` (`root_publish`, `epoch_min`) и ARM64 CI (D-D).

### 3.7. Публикация в процессе

`ArcSwap<ZoneRoot>` на зону: после фазы 2 координатор делает `store(Release)`; читатель — `Acquire`-load. Запись корня в файле нужна recovery/`fsck`/другому процессу. `ZoneRoot` содержит всё, что нужно hot-path (`tree_root`, `meta_root`, `state`, `serial`, `free_head`).

### 3.8. Что остаётся от v1 без изменений

`PageHeader` 40 Б (+`owner_zone`), CRC32C кроме reader region, COW B+tree, RLE, компаратор, фронт-кодирование, restart, split/merge/borrow, Leaf/Branch/Overflow/`ZoneMeta`-раскладки, overflow-поток с разрывом RDATA, `LeafValue` 20 Б, `ZoneState`-семантика, `zone_seq` без переиспользования, tombstone-невидимость, `sync_mode`-семантика, `NEEDS_FSCK`-политика, fail-closed, lock-файл/`O_NOFOLLOW`/`0600`/`fstat`/SIGBUS, двухфазный пин (структура), отсутствие WAL.

## 4. Модель конкурентности

### 4.1. Кто что пишет

| Структура | Писатель | Читатели | Примитив | Частота |
|---|---|---|---|---|
| Superblock, LayoutHead | каталог-writer | все (open) | `pwritev` (A/B + CRC) | создание/расширение |
| Каталог (B+tree) | каталог-writer | `find_zone`/`zones` через индекс | COW + `pwritev` | create / GC |
| Ring корней (A/B-страницы) | координатор (шарды) | recovery/`fsck`; в процессе — `ArcSwap` | `pwritev` (2 копии) | каждый коммит |
| `ZoneRoot` (память) | координатор | читатели | `ArcSwap` Release/Acquire | каждый коммит |
| `reserve_cursor`/`reserve_txn` | все writer'ы | все | CAS в памяти | батч |
| `zone_guard[z]` | координатор, GC | читатели зоны | RMW odd→even | коммит/GC зоны |
| `DP`/`DT`/`D_z`/`RV_z`/`MP(z)` | координатор, GC | writer'ы, GC | store(Release) | пачка/GC |
| `ALLOC_RECORD` | координатор | recovery | `pwritev` (2 копии) | пачка |
| Free pools (per-zone) | writer зоны (free-publish), GC | writer зоны, GC | COW + `pwritev` | группа после drop |
| Reader table | читатели (свои слоты) | GC | атомики + `fence(SeqCst)` | регистрация/пин |
| Данные (leaf/branch/overflow/zone-meta) | writer зоны | читатели | `pwritev`, неизменяемы | коммит |

Нет структуры, которую пишут два потока; нет структуры, которую пишут и читают через файл на hot-path.

### 4.2. Атомики (SEC-PW-014)

`txn`/`page_limit` — CAS `AcqRel`; публикация записи корня — `Release`/`Acquire`; пин — `Release` + `fence(SeqCst)` + `Acquire`; `DP`/`DT`/`D_z`/`RV_z` — `Release`/`Acquire`; `zone_guard` — `AcqRel`; битсет CRC — `Relaxed`; `Relaxed` для публикации запрещён. `loom`-модели: `root_publish`, `alloc_recovery`, `free_publish`, `epoch_min`, `leader_failover`.

### 4.3. Contended cache lines

| Линия | Конкуренция | Смягчение |
|---|---|---|
| `reserve_cursor` | ~0.02 CAS/коммит | экстенты 64 страницы на поток |
| `reserve_txn` | 1 CAS / 64 коммита | `TXN_BATCH` |
| `zone_guard[]`, `ArcSwap[]` | read-mostly, запись — своя зона | выравнивание по 64 Б при > 4096 зон |
| reader slot 128 Б | свой поток; GC читает | 2 линии на слот, `align(64)` |
| каталог | единицы операций в минуту | — |

Копии записи корня лежат в разных страницах (≥ 4 КиБ друг от друга) и не делят torn-сектор; ячейка версии 64 Б, 16 зон на страницу-копию.

### 4.4. Оценка масштабирования

| Ядер | Полезные writer'ы | Узкое место | Оценка зона-коммитов/с |
|---|---|---|---|
| 8 | 6 (1 координатор + 1 GC) | `fsync` (2 на пачку; NVMe 50–200 µs) | 20 000–80 000 при пачке 8–16; 5 000–10 000 при пачке 1–2 |
| 32 | 24 + 2–4 шарда координатора | `fsync` того же inode | тот же потолок; p99 лучше; рост только на крупных батчах |

Числа — оценки; сценарии — `docs/bench/plan.md` (8×8 зон; 8×1 зона — ожидаемая сериализация; компакция + 7 зон).

### 4.5. Предел и следующий шаг

Предел — `fdatasync` одного inode: два синка на пачку. При потребности > ~50k зона-коммитов/с или p99 < 200 µs при `Sync` — WAL (ADR 0003 §8.5): append-only сегменты с group-fsync, checkpoint в per-zone деревья. Ring корней остаётся точкой публикации; WAL — лишь способ сделать данные durable дешевле. Решение — отдельный ADR.

## 5. Протокол коммита

### 5.1. Двухфазный group commit (SEC-PW-005)

Полная последовательность — `parallel-writes-v2` §4.3/§6.2. Инвариант: **фаза 1** (`ALLOC_RECORD` + данные → `fdatasync`), **фаза 2** (корни → `fdatasync`), затем публикация и ack. Корень не пишется, пока `DP > max_allocated_id` и `DT ≥ V`. Лидер группы — с `term`/fencing (`leader_term` в `ALLOC_RECORD`); в M1 — фиксированный координатор (`term = 1`), в M3 — выборный.

### 5.2. Режимы durability

| Режим | Фаза 1 | Фаза 2 | `D_z` | Гарантия |
|---|---|---|---|---|
| `Sync` | да | да | двигается | подтверждённый коммит переживает power loss |
| `Flush` | да (данные+alloc) | корни без fsync | не двигается | переживает рестарт процесса; power loss → откат зоны на `V−1` |
| `Memory` | нет | нет | не двигается | гарантий нет (политика v1 §13.7) |

Липкий `Sync`: после первой durable-группы (`DT > 1`) только `Sync`. `sync()` — глобальный барьер, двигает `D_z` всех зон. `Flush`/`Memory` деградируют неравномерно. При исчерпании ring, если мешает только `D_z` (читателей нет), координатор предпочитает **auto-promotion** в `Sync` (`sync()` поднимает `D_z`), а chain — fallback; иначе chain на `Flush` рос бы на 4 КиБ за коммит.

### 5.3. Область атомарности и видимость

Ровно одна зона; «часть RRset новая» невозможно. Публикация `ArcSwap` (Release): все последующие `zone_snapshot` с `snapshot_seq ≥ V` видят `V`; предыдущие держат старую. Кросс-зонная видимость не гарантируется (PW-L1). `apply` не виден до `commit`. `Abort`/Drop — страницы «never published», реюз немедленный, корень не меняется.

### 5.4. Ошибки и таймауты

`Busy { zone | Catalog | File }` (retryable), `CommitTimeout`, `CommitAborted` (смерть/смена лидера, барьер), `NoSpace { zone }`, `MapFull`, `ZoneQuotaExceeded`, `ZoneWriterStalled { zone }` (только патология: chain исчерпан/нет страницы под запись/I/O), `ZoneDegraded { zone, epoch }` (застрявший `zone_guard`; зона read-only), `ReaderContended` (churn, retryable), `StaleRoot` (нет валидной версии/зона пересоздана), `Corrupt { kind, zone, page }`, `Io`, `AllocWatermarkRegression` (open), `EpochPinned` (только `freeze`/reshape). Семантика — `domain-model` §5.2.

### 5.5. Матрица отказов

Полная — ADR-0006 §7 (`PW-C1..PW-C24`). Ключевые: частичная запись данных → `PW-C1`; до/во время фазы 1 → `PW-C2..C4`; torn одной копии → `PW-C5` (потерь нет); torn двух копий → `PW-C6` (откат ≤ 1 версии); после корней без фазы 2 при падении процесса → `PW-C7`; при power loss → `PW-C8`; часть корней пачки → `PW-C9/C10` (зоны независимы); курсор/`txn` → `PW-C11/C12`; смерть лидера → `PW-C13/C14`; free publish раньше drop → `PW-C15` (порча, ловится `drop_txn ≥ D_z`); donation раньше drop → `PW-C18`; убитый writer → `PW-C19/C23`; чужая `owner_zone` → `PW-C24`.

### 5.6. `strict_corruption = zone` и file-fatal-список

Дефолт v2.0 — **`zone`**: порча, локализованная зоной (ring/chain, `ZoneMeta`, дерево, страницы зоны), делает нечитаемой **только** эту зону; файл открывается и пишет в остальные. Классификация — `parallel-writes-v2` §9.2; ниже — краткая фиксация.

**File-fatal** (файл → read-only + `NEEDS_FSCK` до offline `fsck`; `strict_corruption` **не** применяется):

1. `head.page_limit_at_commit > DP` после `max`-коррекции при open/чтении записи.
2. Пересечение множеств страниц разных зон — `fsck`/scrub.
3. `PageHeader.owner_zone` страницы ≠ владельцу зоны при валидном CRC; `owner_zone`/`version` записи корня от чужой зоны — ленивое чтение.
4. Битый или несовместимый `LayoutHead`, `ALLOC_RECORD` (обе копии), каталог — open.
5. Регрессия `DP`/`DT`/`txn` (`AllocWatermarkRegression`), в том числе ниже уже опубликованной версии из ring/chain.
6. `page.txn > version` у достижимой страницы при валидном CRC (кросс-зонный ABA) — ленивое чтение, `fsck`.

Ошибка: `Corrupt { scope: File, kind }`, `pw_file_fatal_total{kind}`.

**Zone-fatal** (деградирует только зона): обе копии записи torn; `page_limit_at_commit < root_page` у собственной записи; CRC/`page_no`/`payload_len` собственной страницы; `state`/`deleted_txn` несогласованы; `ZoneDegraded`. Опция `strict_corruption = file` возвращает поведение v1 (любая зональная порча → файл read-only).

## 6. Рекламация и GC

### 6.1. `MP(z)` / `RV_z` без сканирования на коммите

GC-проход (10 мс, плюс по требованию при `NoSpace`): один проход по 1024 слотам × 6 пинов → `mp[z]` и `epoch_min`; затем под `zone_guard[z]` пересчёт `RV_z = min(D_z − 1, min(mp[z], epoch_min), freeze_epoch)` и публикация (Release). `freeze_epoch` — EPOCH-пин `FreezeGuard`: удерживает версии, нужные бэкапу/`fsck --at-versions`, и ограничивает рекламацию на время удержания. Писатель читает `RV_z`/`MP(z)` одним load. «Устаревшее низкое» значение только задерживает реюз (safety > availability).

### 6.2. Условие переиспользования

`is_reclaimable(drop_txn, z) = drop_txn ≥ 2 ∧ drop_txn < D_z ∧ drop_txn ≤ RV_z ∧ drop_txn < current_version(z)`. Страницы «never published» — без гейта (A-10). Строгость `< D_z` — та же, что v1 §14: худшая восстановимая версия — `D_z − 1`.

### 6.3. Free pools: «durable drop → free publish»

Порядок (F-10, `parallel-writes-v2` §6.3):

1. `dropped(V)` — страницы, выброшенные в `V`; сразу строится COW-образ bucket'а с `drop_txn = V`, `record(V).free_head = bucket_page`;
2. bucket пишется **в фазе 1 того же коммита** (durable раньше корня, но логически опубликован только через `free_head` в `V`);
3. reuse гейтится `drop_txn < D_z` — не раньше `V+1`, двухгрупповой задержки нет;
4. крах между фазой 1 и корнем → bucket durable, но недостижим (**утечка**, не double-free); `fsck` возвращает (PW-C26).

COW bucket'ов сохраняется. Donation — двумя фазами (`durable drop` → `donate_record` в следующей группе → выдача при `donated_at_txn < DP`), единственный способ перераспределить место между зонами (PW-L3).

### 6.4. Компакция и fsck

`compact_zone` — обычный коммит зоны (перезапись дерева, новый корень); другие зоны не блокируются (PR-3). `fsck`: `owner_zone` каждой страницы, `max_page_id < page_limit_at_commit`, `page.txn ≤ version`, дизъюнктность зон битсетом, `drop_txn < D_z` в пулах, возврат утёкших (`[DP, cursor)`) страниц; `repair --zone <origin>` при `V ≥ D_z − 1` ∧ `V ≥ RV_z`.

## 7. Атомарность между зонами: не нужна

| Операция | Зоно-локальна? |
|---|---|
| DNS-ответ (referral/glue — в той же зоне) | да |
| `commit` правки RRset (INV-1..12 по `ZoneFacts`) | да |
| AXFR/IXFR-out, IXFR-in/AXFR-in | да |
| DNSSEC-подпись | да |
| `create_zone`/`delete_zone` | **нет** (каталог) |
| Экспорт/бэкап набора зон | **нет** |

`create_zone` — каталог-коммит (единственный писатель; `Busy { scope: Catalog }` при занятости). `delete_zone` — коммит корня (tombstone виден мгновенно; GC позже удаляет каталог-запись и возвращает `head_slot`). Пока GC не сработал, «удалить и сразу создать заново» безопасно (PW-L7).

**Что теряем:** нет мгновенного согласованного среза всех зон; `zones()` и содержимое — из разных моментов. **Компенсация:** `freeze()` (maintenance `FreezeGuard`: EPOCH-пин на `published_txn`, публикация `freeze_epoch`, `Drop` снимает; запись при этом не блокируется, но `RV_z` ограничен и файл может расти; таймаут удержания — дефолт 300 с — алерт, **не** вытеснение держателя) для бэкапа/переезда/`fsck --at-versions`; `SnapshotId` = `snapshot_seq` для порядка/аудита (PW-L8). API и домен не обещают межзонную атомарность (SEC-PW-011).

## 8. Что переиспользуется и что меняется

### 8.1. Переиспользуется

Pager/`PageHeader`/CRC/`page_size`; COW B+tree, RLE, фронт-кодирование, restart, split/merge/borrow, overflow; `LeafValue`, `ZoneMeta`-блок, `ZoneState`-семантика, tombstone, `zone_seq`; `sync_mode`/sticky-`Sync`/`NEEDS_FSCK`/fail-closed; двухфазный пин (структура) и «живой читатель не вытесняется»; superblock/секции/feature-флаги; lock-файл/`O_NOFOLLOW`/права/SIGBUS/TOCTOU; bucket-механика (per-zone); recovery/torn-логика (объекты — ring + `ALLOC_RECORD`); `fsck`-обходы.

### 8.2. Меняется

| v1 | v2 |
|---|---|
| meta A/B, полный набор корней | LayoutHead + ring корней + `ALLOC_RECORD` |
| `txnid` как версия файла | `txn` (глобальный) + `version(Z)` |
| `durable_txn`, `reclaim_txn` | `DP`/`DT`, `D_z`, `MP(z)`, `RV_z` |
| глобальный freelist | per-zone пулы + двухфазная donation |
| `oldest_reader_txn` | `MP(z)`/`RV_z` + EPOCH-пин |
| `ZoneEntry` 72 Б | 24 Б идентичности |
| reader slot 32 Б | 128 Б, 6 пинов × 16 Б, seqlock |
| delete = каталог-коммит | delete = коммит корня |
| `Snapshot` = точка файла | `SnapshotHandle` (`snapshot_seq`) + `ZoneSnapshot` |
| «один writer на файл» | «один writer на зону»; M1 `LOCK_EX`, M3 `LOCK_SH` + registry |
| `reserved1` = 0 | `owner_zone` |
| `fsck` глобальный | per-zone + глобальные структурные проверки |

### 8.3. Удаляется

Глобальная meta как структура (`PAGE_TYPE_META` зарезервирован); `durable_watermark`-агрегат; единый `reclaim_txn`; правило «нет читателей ⇒ `oldest_reader_txn = txnid(active)`» (заменено `MP(z) = ∞`).

## 9. Миграция и версионирование

`FORMAT_VERSION_MAJOR = 2`, `MINOR = 0`, `LAYOUT_ID = 2`. Required-флаги: `F_PARALLEL_WRITES` (`owner_zone`), `F_ZONE_HEADS`, `F_EPOCH_VERSIONS`, `F_ALLOC_RECORD`, `F_READER_PINS_V2`, `F_ROOT_DIR`. `PageHeader` и страницы данных не меняются (кроме семантики `reserved1`) — golden-фикстуры v1 переиспользуются.

`zonefile convert --in v1 --out v2` (offline): v1 read-only → создать v2 → для каждой зоны канонический `enumerate` → дерево + `ZoneMeta` → запись корня (`version` = новый `txn`, `page_limit_at_commit`, `state`/`serial`/счётчики из v1 `ZoneEntry`) → каталог идентичности → `ALLOC_RECORD`/LayoutHead/reader region → `fdatasync` + `fsync` каталога + `rename` → `fsck --verify` + сравнение дампов. Свойства: исходник не пишется, идемпотентен, нужно ≈ размер данных + 10 %. v1 под writer'ом v2 → `ReadOnly { reason: ConvertRequired }`; v2 под v1 → `UnsupportedVersion`; даунгрейд не поддерживается.

### 10.3. Отклонения с доказательством

**D-A. Запись корня 64 Б вместо 32 Б — принято Оркестратором.**
Эквивалентность `PW-I7`/`PW-I8`/`SEC-PW-001`: поля `[0,32)` (CRC, `owner_zone`, `version`, `root_page`, `page_limit_at_commit`, `prev_record`, `flags`) сохранены; `[32,64)` — самодостаточные поля зоны, входящие в CRC, поэтому частично записанная запись не даёт валидную версию с чужими `meta_root`/`soa_serial`. Выигрыш: `zones()`/`find_zone`/`/serial` без второй страницы на зону. Цена: 512 Б/зона (25.6 МиБ на 50k зон), 16 зон на страницу-копию.

**D-B. Chain — принят, отклонение закрыто.**
Chain входит в v2.0 (§3.2), поэтому `SEC-PW-002` выполняется буквально: при исчерпании ring версия уходит в chain, писатель не блокируется, `ZoneWriterStalled` остаётся только для патологии (исчерпан `MAX_ROOT_CHAIN_PAGES = 4096`, нет страницы под запись, ошибка I/O). Это же закрывает F-8 ADR-0006 и сценарий «AXFR-пин останавливает запись в активную зону».

**D-C. Курсор аллокатора в памяти, а не в writable-маппинге — принято Оркестратором.**
`PW-I4` требует: durable `page_limit` монотонен, recovery берёт максимум, выдача ниже подтверждённого лимита — всё выполняется через `ALLOC_RECORD`; в M1 один процесс, «увидеть курсор другого процесса» не требуется. Сохранён единственный writable-регион (reader table), SEC-ZF-014 не ослабляется. Для M3 общий durable-курсор обязателен — отдельный ADR (§12.2 п.5), а не скрытая дыра.

**D-D. 6 пинов × u64 вместо 8 × u32 — принято; обязательны `V:loom` и ARM64 CI.**
`SEC-PW-007` предлагает 8 пинов с 32-битной версией; 32-битная версия исчерпывается за ~5 суток при 10⁴ коммитов/с, превращая `NEEDS_FSCK` в штатный режим. 8 × u64 не влезают в 128-Б слот (160 Б). Выбрано 6 × 16 Б. Инвариант `PW-I2` не зависит от числа пинов: при переполнении защита **усиливается** (EPOCH-пин), а не ослабляется.

**Принятые ограничения** (фиксируются в спецификации и API): PW-L1…PW-L12 без изменений.

## 11. Цена и что теряем

| Цена | Оценка | Смягчение |
|---|---|---|
| Сложность | +30–40 % к `pulse-zonefile` (ring, `ALLOC_RECORD`, координатор, пулы, seqlock, `owner_zone`) | альтернатива — глобальный локаут |
| Латентность коммита | +`MAX_BATCH_DELAY` (≤ 1 мс) | настраивается; p99 одной зоны не хуже v1 |
| Throughput | 2 fsync на пачку | честно; следующий шаг — WAL |
| Память/место ring'а | 512 Б/зона (25.6 МиБ на 50k; 512 МиБ на 1M) | ёмкость `max_zones` при создании; offline расширение |
| Фрагментация | per-zone пулы: файл ≈ сумма пиков зон | donation + `compact_zone` + `pw_free_pool_starved_total` |
| Кросс-зонный срез | отсутствует | `freeze()` / offline-копия |
| `Flush`/`Memory` | деградация неравномерна; auto-promotion в `Sync` | документировано |
| `ZoneWriterStalled` | только патология (chain исчерпан/нет страницы/I/O) | per-zone, retryable; штатный AXFR-пин уходит в chain |
| Утечки при крахе | `[DP, cursor)` | `fsck`, `MAX_LEAK_RATIO = 1 %`, алерт |

Не теряем: zero-copy, MVCC без блокировок, crash-safety по зоне, канонический порядок/AXFR/NSEC, отсутствие WAL, один файл, изоляцию повреждения (улучшилась: `Corrupt` несёт `zone`).

## 12. Принятые решения (закрыто) и оставшиеся открытыми вопросы

### 12.1. Принято Оркестратором (не переоткрывать)

| # | Решение | Где зафиксировано |
|---|---|---|
| 1 | **D-A:** `RootEntry` — 64 Б (префикс `[0,32)` совместим с SEC-PW-001, `[32,64)` — поля зоны). | §3.2, §10.3 |
| 2 | **D-B:** **chain входит в v2.0** как safety valve при исчерпании ring 4 версий; писатель не блокируется. `ZoneWriterStalled` — только патология (chain исчерпан/нет страницы/I/O). | §3.2, §5.4, §10.3 |
| 3 | **D-C:** курсор аллокатора и `txn`-билет — в памяти (`AtomicU64`), durable-барьер — `ALLOC_RECORD`; второй writable-регион не вводится. | §3.5, §10.3 |
| 4 | **D-D:** пины — 6 × u64 в 128-Б слоте, двухфазный seqlock + `fence(SeqCst)`; **обязательны** `V:loom` (`root_publish`, `epoch_min`) и ARM64 CI. | §3.6, §4.2, §10.3 |
| 5 | **`max_zones = 65536`** для v2.0 (≈ 32 МиБ ring-региона). Исчерпание — `TooManyZones` (понятная ошибка, без «тихого» роста) + метрика `pw_root_dir_exhausted_total`; расширение — offline compact. | §3.2, `parallel-writes-v2` §4 |
| 6 | **`strict_corruption = zone`** — дефолт; file-fatal — только явный список (§5.6): `page_limit_at_commit > DP`; пересечение множеств зон; `owner_zone`/`version` чужой зоны при валидном CRC; битый `LayoutHead`/`ALLOC_RECORD`/каталог; регрессия `DP`/`DT`/`txn`; `page.txn > version` у достижимой страницы. | §5.6 |
| 7 | **`freeze()`** — минимальный maintenance-вариант: `FreezeGuard` (EPOCH-пин + `freeze_epoch`) для бэкапа/`fsck --at-versions`; запись не блокирует, но `RV_z` ограничен; таймаут удержания — алерт, не вытеснение. | §7 |
| 8 | **M1 — один процесс** (`flock(LOCK_EX)`); межпроцессная запись **запрещена** до отдельного ADR (M3, `LOCK_SH` + registry + общий durable-курсор). | §5.1, §10.1 (009) |
| 9 | **Snapshot ceiling = ∞:** `SnapshotHandle` — каталог + `SnapshotId` (аудит/диагностика); `zone_snapshot` читает последнюю опубликованную версию зоны. Согласованный срез — только `freeze()`. | §3.4, §3.6 |

### 12.2. Оставшиеся открытые вопросы

1. **`MAX_BATCH_DELAY`/`MAX_BATCH_ZONES`/`MAX_BATCH_BYTES`** — калибровка на M3 (значения по умолчанию: 1 мс / 256 / 1 МиБ).
2. **Chain-порог и бюджеты:** `MAX_ROOT_CHAIN_PAGES = 4096` (ёмкость) и `MAX_ROOT_CHAIN_HOPS = 4096` (обход) — подтвердить после нагрузочных прогонов; алерт `pw_root_chain_depth{zone}`.
3. **Шарды зоны (вариант B).** Триггер: зона > 5M RRset **и** > 100 коммитов/с в неё.
4. **WAL.** Порог пересмотра ADR: устойчиво > 30k зона-коммитов/с или p99 < 200 µs при `Sync`.
5. **M3 ADR:** `LOCK_SH` + writer registry + общий durable-курсор (правка SEC-ZF-014) + `Snapshot`-семантика для межпроцессных читателей.
6. **`freeze()`-таймаут:** предельное время удержания retention-пинов и поведение при отказе writer'ов отдать lease.
