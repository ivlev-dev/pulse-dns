# ADR 0003. Формат файла зон: page-based COW B+tree с двойным meta-заголовком

- **Статус:** предложено (на утверждение Оркестратором)
- **Дата:** 2026-11-23
- **Этап:** M1
- **Связанные документы:** `docs/adr/0001-ddd-architecture.md`, `docs/adr/0002-crate-map.md`, `docs/adr/0004-security-model.md` (SEC-ZF-001..014 — источник истины по ID), `docs/spec/domain-model.md` (§5.1 `ZoneStore`, §5.2 `ZoneWriter`), `docs/spec/zonefile-v1.md`, `docs/spec/io-uring-runtime.md`, `docs/bench/plan.md`
- **Реализует:** адаптер портов `ZoneStore` / `ZoneWriter` в крейте `pulse-zonefile`

---

## 1. Контекст

Зафиксировано пользователем и не обсуждается:

1. **Один файл содержит все зоны**, подключается через `mmap`, поиск зоны по имени быстрый.
2. **Обновление зон — инкрементальные правки прямо в файле** (не полная пересборка). Отсюда обязательны: crash safety, MVCC-читатели, единственный писатель, восстановление после падения.
3. Транспорты v1: UDP + TCP + REST; зоны primary + secondary (AXFR/IXFR/NOTIFY) + forward; DNSSEC sign+validate в v1.

Из DDD-контракта (`docs/spec/domain-model.md`) формат обязан обеспечить:

| Требование порта | Следствие для формата |
|---|---|
| `ZoneStore::snapshot()` — O(1), lock-free, без аллокаций, ≤ 20 ns на клон | снапшот = `Arc` над неизменяемым состоянием + атомарный указатель на текущий txn |
| `ZoneStore::lookup` — zero-copy, результат живёт не дольше снапшота | данные ответа должны лежать в `mmap` в готовом к отправке виде; срезы, не копии |
| p50 ≤ 500 ns, p99 ≤ 2 µs на зону 1M RRset в горячем кеше CPU | ≤ 3 уровней дерева, ≤ 6 cache miss на lookup |
| `enumerate` — стабильный канонический порядок `(owner, type)` | ключи упорядочены в DNSSEC-каноническом порядке (RFC 4034 §6.1) |
| читатель держит снапшот неограниченно долго, писатель не переиспользует его страницы | таблица читателей в файле + строгая граница `free_txn < durable_watermark` и `free_txn ≤ oldest_reader_txn` |
| `commit` атомарен и crash-safe; `Durability::{Memory,Flush,Sync}` | три режима sync + протокол «данные → fsync → meta» |
| `apply` не виден до `commit` | COW: новые версии страниц по новым номерам, публикация только через meta |
| один писатель, эксклюзивное владение | `flock(LOCK_EX\|LOCK_NB)` + таблица читателей только для читателей |

Из threat-model: self-describing header, checked math, bounds checks, page checksums, bounded counts, fail-closed, `O_NOFOLLOW`, `fstat`-проверка owner/mode/dev/ino, обработчик SIGBUS, режим 0600.

**Не-цели v1:** распределённая запись, несколько писателей, онлайн-shrink файла, NSEC3-дерево, компрессия RDATA-имён, шифрование файла.

## 2. Проверяемые требования

| ID | Требование | Как проверяется |
|---|---|---|
| R1 | Инкрементальная правка: стоимость коммита O(глубина дерева + изменённые RRset), не O(размер зоны) | бенчмарк: 1 запись в зоне 1M RRset — записано ≤ 64 страниц |
| R2 | Atomicity: после краха виден либо старый, либо новый снапшот целиком | kill -9 в случайной точке, 10⁴ итераций, `fsck --verify` |
| R3 | Durability: `Sync` — подтверждённый коммит не теряется при power loss | тест с `dm-flakey`/выключением питания, счётчик подтверждённых txn сверяется после рестарта |
| R4 | Чтение без материализации: inline-RDATA — срез `mmap`; overflow-RDATA — `chunks()`/`copy_into` **одного RR**; набор и зона не материализуются никогда | API `RdataRef`; профиль: 0 копий для inline, ≤ 1 копии на RR для overflow, нет копий размером с RRset |
| R5 | N читателей / 1 писатель без блокировок на hot-path | писатель не берёт блокировок читателя; `lookup` не содержит атомарных RMW |
| R6 | Восстановление после SIGKILL/power loss без ручных действий | авто-выбор max-valid meta-близнеца; `Sync`/`Flush` — без ручных действий, `Memory` — `NEEDS_FSCK` + явный `allow_unsynced_memory_recovery` (осознанное исключение) |
| R7 | Fail-closed на повреждении: никогда не отдавать частичные/битые данные | отказ `Corrupt` + SERVFAIL, без «догадок» |
| R8 | Расширяемость формата: новая версия не ломает старого читателя | таблица секций + `required/optional` feature-флаги |
| R9 | Один файл, много зон, быстрый поиск зоны | индекс зон в памяти, 15–40 ns на поиск |
| R10 | Файл — источник правды для AXFR/IXFR и DNSSEC-подписи | канонический обход без сортировки в памяти |
| R11 | Форматная готовность к DNSSEC в v1: RDATA хранится в канонической wire-форме (без перекодирования), порядок ключей = RFC 4034 §6.1, `RRSIG` различается по covered type, NSEC-цепочка получается обходом | golden-тесты канонизации (NSEC-порядок, сортировка RR внутри RRset, отсутствие компрессии в RDATA) |
| R12 | Жизненный цикл зоны атомарен: `Initializing → Serving → Tombstone`, `zone_seq` не переиспользуется, страницы освобождаются только после `reclaim_txn` | kill -9 в момент создания/удаления; `fsck`: нет висящих страниц и «оживших» `ZoneId` |
| R13 | Freelist корректен: страница не выдаётся дважды, не выдаётся в той же транзакции и не выдаётся при `free_txn ≥ durable_watermark`; bucket-страницы не текут | property-тест (случайные upsert/delete + `fsck`); число bucket-страниц не растёт на стабильной нагрузке |

### 2.1. Принятые целевые метрики (зафиксировано Оркестратором)

| Операция | Цель p50 | Цель p99 | Примечание |
|---|---|---|---|
| Поиск зоны (longest-suffix по индексу) | 15–40 нс | ≤ 120 нс | десятки нс достижимы: хеш-пробы, без диска |
| Поиск RRset в зоне 1M, тёплый кеш | ≤ 500 нс (цель порта: 300 нс) | ≤ 2 µs | совпадает с целью порта `ZoneStore` (`domain-model` §5.1) |
| `commit` 1 RR (`Sync`, NVMe) | ≤ 2 мс | ≤ 5 мс | миллисекунды: два `fdatasync` |
| `commit` 1 RR (`Memory`) | ≤ 200 µs | ≤ 600 µs | без fsync |

> **Замена формулировки задания.** Исходная цель «lookup зоны и RRset — наносекунды/десятки нс» принята только для поиска зоны. Для RRset в зоне 1M она физически недостижима: 2–3 уровня дерева × 1–2 cache miss дают 150–500 нс. Целевые числа выше — согласованный компромисс; архитектура при этом **не** меняется на резидентный индекс в RAM (он противоречил бы «один файл — источник правды» и zero-copy).

## 3. Альтернативы

### A. Append-only лог записей + периодическая компакция

Правки дописываются в конец файла (WAL-подобно), периодически — полная перезапись в новый файл с `rename`.

- **+** Простейшая crash safety: дописал + `fsync` = коммит; нет page allocation, нет freelist.
- **+** Последовательная запись — лучший паттерн для SSD/NVMe.
- **−** Чтение требует индекса в памяти, построенного при открытии сканированием лога: **O(размер зоны)** на старте. Для 10M RRset это секунды и гигабайты heap — прямо противоречит «mmap + zero-copy» и R4/R9.
- **−** Либо индекс на диске (тогда это уже B-дерево + лог, т.е. вариант B плюс лишняя сущность), либо индекс только в RAM (тогда файл не самодостаточен, ломается R4 и «один файл — источник правды»).
- **−** Компакция — это полная пересборка: окно, в котором нужно либо вдвое больше диска, либо stop-the-world. Против требования «инкрементальные правки».
- **−** Живые читатели держат старые сегменты → нужна та же машинерия эпох/refcount, что и в B, но плюс рост файла.

**Вердикт:** отклонён. Даёт дешёвую durability, но не даёт zero-copy и упирается в O(N) на открытии.

### B. LMDB-подобное COW B+tree с двумя meta-страницами

Дерево страниц фиксированного размера, правка = копирование пути от корня до листа в новые страницы, коммит = запись второго meta-заголовка с новым `txnid`.

- **+** Инкрементальность R1 из коробки: O(depth) страниц на коммит.
- **+** Crash safety без журнала: старый meta всегда цел (двойной заголовок + CRC + `txnid`), порядок «данные fsync → meta» даёт атомарность.
- **+** Zero-copy: страницы `mmap`-нуты, значения — самодостаточные байтовые блоки; читатель получает срезы.
- **+** MVCC бесплатно: старая версия страницы физически не перезаписывается, пока её видит читатель.
- **+** Канонический порядок = порядок ключей → AXFR/NSEC/`enumerate` без сортировки.
- **−** Фрагментация: файл не сжимается, освобождённые страницы переиспользуются только при отсутствии читателей.
- **−** Нужны: freelist, таблица читателей, детект утечек страниц, `fsck`.
- **−** Стоимость коммита = 2 `fsync` (data, meta) в режиме `Sync`.

**Вердикт:** принят как основа.

### C. Собственный page-based heap + отдельный индекс

Своя куча (аллокатор объектов переменного размера) + отдельная индексная структура (хеш или B+tree) поверх.

- **+** Максимальная гибкость под переменные RRset.
- **−** Две подсистемы вместо одной: аллокатор кучи сам требует metadata, фрагментации, crash-safe free-list, компакции. Это ~2× объём кода и ~2× поверхность багов при том же результате.
- **−** Индекс всё равно нужен упорядоченный (AXFR/NSEC) → B+tree; тогда куча избыточна.
- **−** Zero-copy достижим, но поддержка «объект переменного размера + переиспользование» без MVCC-страниц возвращает те же проблемы.

**Вердикт:** отклонён. B — это и есть «куча + индекс», где куча = страницы, а индекс = дерево.

### D. Полная перезапись файла + атомарный `rename`

- **+** Тривиально корректно, нет фрагментации.
- **−** Противоречит требованию инкрементальности; 10M RRset = секунды на правку; двойной расход диска.
- **Вердикт:** только как offline-компакция (см. §7.4), не как рабочий режим.

### E. Файл на зону

- **+** Изоляция порчи, независимые коммиты.
- **−** Прямо противоречит решению «один файл»; тысячи `mmap` и `fsync`; нет атомарности между зонами (а IXFR-out и DNSSEC-подпись требуют согласованного снапшота).
- **Вердикт:** отклонён.

## 4. Решение

**Принят вариант B** в следующей конкретизации (детали — в `docs/spec/zonefile-v1.md`):

1. **Две ступени деревьев.** Глобальное дерево каталога зон (ключ — apex-имя) и по дереву на зону (ключ — `owner | type | class | subtype`). Фактическая глубина — 2–3 при лимите формата 8.
2. **Фронт-кодирование ключей** в leaf/branch-страницах (`shared_len` + суффикс + restart-точки каждые 8 записей). Для DNS это одновременно и prefix-, и suffix-компрессия: RLE-ключи соседних имён делят общий хвост домена.
3. **RLE-ключи**: имя хранится в каноническом lowercase wire-формате с обратным порядком меток (`com` `example` `www` `\0`). Порядок сравнения — DNSSEC-канонический (RFC 4034 §6.1), реализуется компаратором, а не `memcmp` (см. §8.2).
4. **RDATA хранится дословно** (uncompressed wire-format) с инвариантом загрузчика «RDATA одновременно является DNSSEC-канонической формой». RDATA **может разрываться между страницами** overflow-цепочки (решение Оркестратора): так `rdlength` доходит до протокольных 65 535, а не упирается в размер страницы. Чтение — `RdataRef`: `as_slice()` для непрерывных байт, `chunks()`/`copy_into()` для разорванных; материализация набора запрещена, копируется максимум один RR. Компрессия имён внутри RDATA отклонена в v1 (§8.3).
5. **Meta-страницы: две**, `txnid` монотонен, активна **самая новая валидная meta** (max `txnid`, прошедшая проверку против superblock), а не «`txnid ≤ durable_txn`» (§5.4). **Единый `durable_watermark`** = `max(min(durable_txn, txnid))` по всем валидным meta; recovery и runtime (`effective_mode`/`check_commit`/`reclaim`) используют только его, не `durable_txn` выбранной meta. Худшая восстановимая meta — `durable_watermark − 1`. Каждая meta содержит полный набор корней. Плюс две копии superblock с persistent-полями `sync_mode` (`0=Sync`, `1=Flush`, `2=Memory`) и `sync_mode_version` (`1`; обе копии обязаны хранить и совпадать; §4.1 спецификации).
6. **Freelist** — связный список bucket-страниц, упорядоченный по `free_txn`; переиспользование разрешено только при `free_txn < durable_watermark` (**строго**) и `free_txn ≤ oldest_reader_txn`, то есть `free_txn ≤ reclaim_txn = min(durable_watermark − 1, oldest_reader_txn)`, и `free_txn < current_txn` (защита от двойного освобождения). Строгость по watermark обязательна: страницы, освобождённые в `F = durable_watermark`, ещё достижимы из худшей восстановимой meta `watermark−1`. При `durable_watermark = 1` `reclaim_txn = 0` — переиспользование невозможно, нужен периодический `sync()` (§5.2). Bucket-страницы выделяются из eligible-страниц, иначе из high-water (без рекурсии), и возвращаются в freelist при опустошении — утечек нет. B+tree для freelist отклонён: список короче, не требует COW-пути и даёт O(depth) коммит.
7. **Таблица читателей в файле** (1024 слота, атомарные `u64`), чтобы писатель знал, какие снапшоты ещё живы. Регион — **единственный** writable-маппинг (`PROT_READ|PROT_WRITE`, `MAP_SHARED`, `off % 64 == 0`, длина из `page_size`); всё остальное `PROT_READ`, запись через `pwritev`. Собственный 32-байтовый дескриптор страницы, `payload_len = page_size − 32`, CRC исключён. Межпроцессно в M1 не требуется; тесты — M3.
8. **Три режима durability**, отображённые на порт: `Durability::Sync → MODE_SYNC` (дефолт), `Flush → MODE_NOMETASYNC`, `Memory → MODE_NOSYNC` (экспериментальный, по умолчанию выключен). Режим — persistent-свойство файла (`superblock.sync_mode`, §4.1 спецификации): `Sync`/`Flush`-файл не принимает коммит слабее своего режима (`DurabilityBelowFileMode`). Поверх этого действует **липкое повышение**: после первого успешного `Sync`/`sync()` (`durable_watermark > 1`) все коммиты обязаны быть `Sync`, иначе два слабых коммита затрут durable-слот и power loss откатит ниже подтверждённого `Sync`. `Flush` переживает рестарт процесса (данные fsync'нуты до meta), но не гарантирует power loss; `Memory` не даёт гарантий: recovery сначала чисто откатывается на meta `≤ durable_watermark`, иначе требует `allow_unsynced_memory_recovery` + `NEEDS_FSCK` и открывает файл read-only до offline `fsck`.
9. **Заголовок страницы — 40 байт**, `txn` — `u64` (wrap-safe сравнение с `u64` обходится дороже 8 байт на страницу). `payload_len` включает заголовок; для reader table — `page_size − 32`.
10. **Жизненный цикл зоны:** `ZoneEntry` + `meta_root` на per-zone блок (настройки, SOA-таймеры, upstreams), `ZoneState ∈ {Initializing, Serving, Tombstone}`. Удаление — tombstone: зона мгновенно исчезает из поиска, страницы дерева/блока освобождаются только при `reclaim_txn ≥ txnid(удаления)`; `zone_seq` не переиспользуется.

## 5. Гарантии

### 5.1. Atomicity

Транзакция либо целиком видна, либо целиком не видна. Механизмы:

- все изменяемые страницы пишутся **по новым номерам** (COW), ни одна страница, достижимая из активного meta, не перезаписывается;
- публикация = запись **одной** meta-страницы (второй из пары), которая до этого не была активной;
- meta валидируется целиком по `crc32c` + `page_no` + `txnid` + версии;
- при открытии активна meta с максимальным `txnid` среди валидных; «полу-валидная» невозможна: либо CRC сходится, либо нет.

Промежуточных состояний «часть RRset новая, часть старая» не существует: RRset — единое значение (inline или overflow-цепочка), а дерево обновляется одним путём.

### 5.2. Durability

**Соответствие порта и режимов формата** (`Durability` из `docs/spec/domain-model.md` §5.2):

| Порт | Режим формата | Что делает `commit` | Гарантия после возврата |
|---|---|---|---|
| `Durability::Sync` | `MODE_SYNC = 2` | `writev` данных → `fdatasync` → `write` meta → `fdatasync` | коммит на диске |
| `Durability::Flush` | `MODE_NOMETASYNC = 1` | `writev` данных → `fdatasync` → `write` meta (без fsync) | данные на диске, meta в page cache; коммит виден после рестарта процесса, но не гарантирован при power loss |
| `Durability::Memory` | `MODE_NOSYNC = 0` | только `write*` в page cache | виден читателям процесса; гарантий после рестарта/потери питания нет |

**`msync` как штатный путь коммита не используется.** Маппинг **данных** (superblock, meta, деревья, overflow, freelist, zone meta) — только `PROT_READ`, `MAP_SHARED`; запись идёт исключительно через `pwritev` по заранее вычисленным смещениям, а durability — через `fdatasync`. Единственное исключение — регион таблицы читателей: он маппится отдельно как `PROT_READ|PROT_WRITE` (см. §4 п.7, §5.3); к данным зон этот маппинг не даёт доступа. Причины: (а) `msync` не задаёт порядок «данные → meta», на котором держится атомарность; (б) `msync(MS_SYNC)` синхронизирует диапазон без учёта границ транзакции и дороже; (в) грязные страницы `MAP_SHARED` могут уходить на диск в произвольный момент, что ломает контроль порядка. Read-only маппинг при этом видит данные, записанные `pwritev` в тот же inode (когерентность page cache), поэтому writer может перечитывать и валидировать только что записанные страницы без writable-маппинга. Согласовано с DDD-архитектором (`domain-model` §5.2).

| Режим | Потеря при power loss |
|---|---|
| `Sync` (`MODE_SYNC`) | ни одного подтверждённого коммита |
| `Flush` (`MODE_NOMETASYNC`) | коммиты, чья meta не долетела на диск; данные выбранной восстановлением meta fsync'нуты, файл валиден; если оба слота не долетели/битые — `CorruptNoValidMeta`. После **рестарта процесса** потерь нет. Применимо только до первого `sync()`: после него режим липко `Sync` |
| `Memory` (`MODE_NOSYNC`) | неподтверждённые коммиты до первого `sync()` (после него режим липко `Sync`); meta могла пережить данные → recovery сначала чисто откатывается на meta `≤ durable_watermark`, иначе требует `NEEDS_FSCK` + `allow_unsynced_memory_recovery` и открывает файл read-only до offline `fsck` |

**Правило восстановления (B-12, ревизия 1.5.3).** Активна **самая новая валидная meta** (max `txnid`), прошедшая проверку против superblock. `durable_watermark = max(min(durable_txn, txnid))` по всем валидным meta; если `durable_txn(selected) < durable_watermark` — нарушение монотонности (W-10): `NEEDS_FSCK` + `write_locked`, read-only до offline fsck. Если `txnid > durable_watermark`:
- `sync_mode ∈ {Sync, Flush}` — meta принимается, `recovered_unsynced = true`, `NEEDS_FSCK` не выставляется: данные fsync'нуты до meta, а страницы с `free_txn ≥ durable_watermark` не переиспользовались;
- `sync_mode == Memory` — meta могла пережить данные: recovery сначала пытается открыть самую новую валидную meta с `txnid ≤ durable_watermark` (чисто, теряются только неподтверждённые Memory-коммиты; если её `durable_txn` ниже watermark — W-10, read-only). Если такой нет — обязателен `OpenConfig.allow_unsynced_memory_recovery = true`, иначе отказ `UnsyncedMemoryRecovery`; с флагом — `NEEDS_FSCK` (в памяти/Stats, meta не переписывается) и **read-only до offline fsck**.

Runtime `effective_mode`/`check_commit`/`reclaim_txn` используют тот же `durable_watermark`, а не `durable_txn` выбранной meta; иначе sticky обходится метой с меньшим `durable_txn`.

Torn/невалидная одна meta при валидной второй — **штатный крах** (`torn_meta = true`, диагностика, без `NEEDS_FSCK`). Если обе meta невалидны — `CorruptNoValidMeta` (открывать нечего); `NEEDS_FSCK` — если у невалидного слота **декодируется** `txnid >` выбранного (риск потерянного коммита) либо есть иная неопределённость; нечитаемый `txnid` сам по себе — не повод для `fsck`.

`durable_watermark` **не понижается** при recovery: это единый watermark переиспользования (§4 п.6/§5.4). Иначе приём `Flush`-meta легализовал бы переиспользование страниц выше последней fsync'нутой meta, и последующая потеря meta откатила бы восстановление на перезаписанные страницы.

**`Memory` (NOSYNC).** Режим не даёт гарантий сохранности: ни при потере питания, ни при падении процесса (recovery не отличает их). Данные и meta пишутся только в page cache; ядро вправе записать meta раньше данных, поэтому валидная meta `T > durable_watermark` может ссылаться на отсутствующие данные. Если есть валидная meta `txnid ≤ durable_watermark`, recovery открывает её чисто (теряются только неподтверждённые Memory-коммиты; при её `durable_txn < durable_watermark` — W-10, read-only). Иначе без `allow_unsynced_memory_recovery` — отказ `UnsyncedMemoryRecovery`; с флагом — `NEEDS_FSCK`, файл **read-only до offline `fsck`** и ленивые проверки (`page.txn ≤ snapshot.txnid`, CRC, границы, `payload_len`) на каждом чтении; freelist не используется для выдачи. Консистентность восстановленного состояния не гарантируется без `fsck`; гарантируется только структурная валидность страниц. Режим помечен `EXPERIMENTAL`, по умолчанию выключен (`DEFAULT_SYNC_MODE = Sync`).

**`sync()` обязателен для прогресса в `Flush` и `Memory`:** `fdatasync` данных → запись новой meta `txnid+1` в неактивный слот (те же корни, `durable_txn = txnid+1`) → `fdatasync` meta → публикация. Без него `durable_watermark` не растёт, `reclaim_txn` стоит (при `durable_watermark = 1` равен 0), freelist голодает и возможен `NoSpace`/`MapFull` при свободном месте. Для `Flush` это цена безопасного восстановления: переиспользовать страницы выше последней fsync'нутой meta нельзя. Кроме того, `sync()` — **односторонний чекпойнт**: после него `durable_watermark > 1` и режим навсегда становится `Sync` (понижение запрещено, §4 п.8). Эксплуатационно writer обязан вызывать `sync()` не реже `SYNC_INTERVAL_MS` и/или при приближении к `MapFull`, а также перед graceful shutdown; метрики — `durable_lag_txns = txnid(active) − durable_watermark` и `freelist_eligible_pages`.

> В режиме `Memory` `Writer::close()` (и graceful shutdown) **обязаны** выполнить `sync()` (fsync данных + запись/fdatasync meta), а не только `fdatasync` данных; иначе подтверждённой meta не появится и потеря — весь сеанс. `sync()` при этом необратимо переводит файл в липкий `Sync`. Аварийное завершение процесса — эквивалент power loss.

Правила, без которых режимы небезопасны:

- **`fdatasync` данных всегда выполняется до записи любой meta** (кроме `Memory`, где данных тоже не синхронизируем — тогда и переиспользовать освобождённые страницы нельзя до явного `sync()`). При group commit синхронизируются **все** диапазоны данных нескольких готовых коммитов; порядок диапазонов между собой не важен, но «данные до meta» строгий.
- **`Flush` не двигает `durable_watermark`:** meta не fsync'ится, поэтому последней гарантированно записанной meta остаётся последний `Sync`/`sync()`. Это удерживает `reclaim_txn` ниже неподтверждённой meta; приём `Flush`-meta при recovery watermark не повышает.
- Каждая meta самодостаточна (полный набор корней), поэтому восстановление не зависит от порядка записи мет и не требует чтения предыдущей.
- `durable_watermark` монотонно растёт только после успешного `fdatasync` **meta** (`Sync`/`sync()`), а не после `Flush`/`Memory`; freelist не выдаёт страницы с `free_txn ≥ durable_watermark` даже при `free_txn ≤ oldest_reader_txn`. `durable_txn(selected) < durable_watermark` → `NEEDS_FSCK` + read-only (W-10).
- После `durable_watermark > 1` коммит только `Sync` (липкий режим): два слабых коммита затёрли бы durable-слот, и power loss откатил бы состояние ниже подтверждённого коммита.
- Страницы, освобождённые в транзакции `T`, не выдаются в `T` (двойное освобождение) — они ещё достижимы из `meta(T-1)`.
- `superblock.sync_mode` и `superblock.sync_mode_version` — неизменяемые **сохраняемые** поля файла: хранятся в структуре, пишутся при encode, сравниваются A/B. Коммит слабее floor (файлового режима или липкого `Sync`) отклоняется `InvariantViolation(DurabilityBelowFileMode)` (§4.1 спецификации). Иначе recovery доверился бы `sync_mode` и принял бы meta без fsync данных.
- Создание нового файла — строгая последовательность (superblock → начальная meta → reader table → `fdatasync` + `fsync` каталога); до её завершения файл не считается созданным (`docs/spec/zonefile-v1.md` §4).

### 5.3. Конкурентность и snapshot isolation

- **N читателей / 1 писатель.** Читатели никогда не блокируются: они читают meta, фиксируют `txnid` и работают по неизменяемому графу страниц.
- **Snapshot isolation** (не serializable): читатель с `txn = T` видит ровно состояние после коммита `T` и не видит более поздних. Повторный `lookup` в том же снапшоте детерминирован (требование `ZoneStore`).
- **Писатель один** на файл: **отдельный lock-файл** `<zonefile>.lock` (0600) с `O_NOFOLLOW` + `fstat` (regular-file) и `flock(LOCK_EX | LOCK_NB)`; второй писатель получает `Busy`, не regular → `NotRegularFile`, lock снимается смертью процесса. Блокировка на самом файле зон не берётся (SEC-ZF-009).
- **Читатели не берут `flock` вообще.** Они регистрируются только в таблице читателей (§6 спецификации), поэтому не блокируют писателя и не блокируются им. Файл открывается `O_RDWR` и читателем (нужны права на запись: он пишет слоты в writable-регион reader table), при этом данные маппятся `PROT_READ`. В M1 читатели внутрипроцессные; межпроцессные — M3.
- **Писатель не ждёт читателей** на пути коммита: он только читает `oldest_reader_txn` (атомарно) и не выдаёт «молодые» страницы из freelist.
- Если все свободные страницы «молодые» (`free_txn ≥ durable_watermark` или `free_txn > oldest_reader_txn`; эквивалентно `free_txn > reclaim_txn = min(durable_watermark−1, oldest_reader_txn)`; при `durable_watermark = 1` — все) — коммит возвращает `NoSpace` (retry после `sync()`/освобождения читателей), а не портит данные; при исчерпании `page_count_max` — `MapFull`. Метрика `freelist_starved_total`, `freelist_eligible_pages`, `durable_lag_txns`.
- **Writable-маппинг ровно один:** регион таблицы читателей (`PROT_READ|PROT_WRITE`, `MAP_SHARED`, `off % 64 == 0`, длина из `page_size`). Данные, деревья, overflow, meta — строго `PROT_READ`; запись — `pwritev` (SEC-ZF-014).

### 5.4. Восстановление после SIGKILL / power loss

При открытии (детали — `docs/spec/zonefile-v1.md` §13.7):

1. Читаются обе копии superblock; валидной считается та, у которой сходится CRC и совпадают `magic/version/page_size`. `sync_mode` и `sync_mode_version` хранятся как поля, пишутся при encode и сравниваются A/B наравне. Расхождение `page_size`/`page_count_max`/`instance_uuid`/`sync_mode`/`sync_mode_version` между копиями (в частности `A: version=1, B: version=0`) → `Corrupt` (fail-closed). Неизвестный `sync_mode` (`> 2`) → `Corrupt`, неизвестная версия поля (`∉ {0,1}`) → `UnsupportedVersion` (§4.1 спецификации).
2. Читаются обе meta; структурно валидные (CRC + `page_no` + версия + `page_size`). `durable_txn` **не** используется как фильтр выбора.
3. Активна **самая новая валидная meta** (max `txnid`, tie-break — больший слот), прошедшая проверку против superblock. `durable_watermark = max(min(durable_txn, txnid))` по всем валидным meta; `durable_txn(selected) < durable_watermark` → W-10: `NEEDS_FSCK` + `write_locked`, read-only до offline fsck. Обе meta содержат полный набор корней, поэтому откат на `T-1` не требует чтения `T`. Худшая восстановимая meta — `durable_watermark − 1`; переиспользование страниц разрешено только при `free_txn < durable_watermark` (§4 п.6).
4. Политика `txnid > durable_watermark`: `Sync`/`Flush` → принять, `recovered_unsynced = true`, без `NEEDS_FSCK` (данные fsync'нуты до meta; `free_txn ≥ durable_watermark` не переиспользовались); `Memory` → сначала попытаться принять самую новую валидную meta с `txnid ≤ durable_watermark` (чисто, теряются только неподтверждённые Memory-коммиты; при её `durable_txn < watermark` — W-10, read-only); если такой нет — `allow_unsynced_memory_recovery` обязателен, иначе `UnsyncedMemoryRecovery`, а с флагом — `NEEDS_FSCK` + read-only до offline `fsck`. Watermark не понижается.
5. Torn/невалидная одна meta при валидной второй — **штатный крах**: `torn_meta = true` (диагностика), `NEEDS_FSCK` **не** выставляется; пустой слот в initial-файле — норма. Обе невалидны → `CorruptNoValidMeta`. `NEEDS_FSCK` — если у невалидного слота декодируется `txnid >` выбранного (риск потерянного коммита) либо есть иная неопределённость (аномально пустой слот при `active.txnid > 1`). Нечитаемый `txnid` — не повод для `fsck`. Если выбранная meta не проходит проверку границ/high_water/reader region → `Corrupt`, без отката на более старую.
6. Проверяется `page_count_high_water ≤ page_count_max` и размер файла (усечение → `TruncatedFile`, **не** SIGBUS).
7. Границы корней и региона таблицы читателей проверяются без полного обхода; целостность страниц — лениво по CRC и целиком `fsck --verify`.
8. Таблица читателей санируется **только** по мёртвому PID или несовпадению `incarnation` (при `incarnation ≠ 0`); при этом `NEEDS_FSCK` выставляется **всегда** (независимо от `active_txn`/`flags`). `incarnation = 0` — «неизвестен» (probe вернул `Unknown` при регистрации): слот считается живым, **не вытесняется**, `NEEDS_FSCK`. `ProcessProbe::Unknown` (EACCES/parse error/`/proc` недоступен) → считать живым, не вытеснять, `NEEDS_FSCK`. `heartbeat` старше `stale_reader_timeout` — это диагностика (`readers_stalled`, предупреждение для `LONG_HOLD`), **не** основание для вытеснения: живой, но остановленный читатель не вытесняется никогда (SEC-ZF-007).

Матрица точек отказа — в `docs/spec/zonefile-v1.md` §15.

### 5.5. Поведение при повреждении

- Любая страница проверяется по `crc32c`, `page_type`, `page_no` (номер внутри страницы должен совпадать с номером слота) и `txn` при каждом чтении **один раз** (результат кешируется в per-snapshot bitset).
- Нарушение инвариантов (ключи не возрастают, дочерний указатель вне диапазона, длина за пределами страницы, цикл в overflow-цепочке, `depth > 8`) → `StoreError::Corrupt`, ответ SERVFAIL, инкремент `zonefile_corrupt_total{kind}`, **без** попыток «починить на чтении».
- Читатель не отдаёт частичный RRset: значение либо целиком валидно, либо ошибка.
- Bit-rot не восстанавливается (нет избыточности): рекомендуется checksummed ФС/RAID; отдельная секция с манифестом BLAKE3 зарезервирована (`section id 6`).
- `zonefile fsck --verify` — полный обход с проверкой порядка ключей, достижимости, отсутствия циклов, сверкой freelist.
- `--repair` умеет откатиться на предыдущий meta и вернуть утёкшие страницы, но **только** при `T ≥ durable_watermark − 1` **и** `T ≥ oldest_reader_txn` для целевого `T` (иначе страницы, освобождённые после `T`, могли быть переиспользованы или удерживаются читателем → `RefuseToRollback`). Авторемонта на старте нет.

### 5.6. Hot-reload и переключение снапшотов

- Публикация: `commit` завершает запись meta, выполняет `fence(Release)` и делает `atomic_store(active_snapshot, new)`; подписчики — через `SnapshotPublisher` (внутренний порт `pulse-zonefile`).
- В процессе: `SnapshotHandle` = `Arc<SnapshotInner>`; `SnapshotInner { mapping: Arc<Mmap>, txn: u64, reader_slot: ReaderSlot }`. Клон ≤ 20 ns, без syscall (требование порта).
- Сервер берёт снапшот **на батч запросов** (например, на один `recvmmsg`-батч), а не на запрос: одна атомарная загрузка на 32–64 запроса, при этом все ответы батча согласованы.
- Открытие/закрытие reader-слота: `open` — CAS в таблице читателей; `drop` — `active_txn = 0` + `Release`. **Слот на поток** (до 4 слотов на поток для вложенных снапшотов); `Clone` снапшота не пиннит повторно (refcount внутри `SnapshotInner`), `unpin` — на `Drop` последнего держателя. Writer читает слоты с `Acquire`.
- Переключение зоны из файла (reload с диска) — обычная транзакция: весь набор правок одной зоны коммитится атомарно, читатели видят либо старую, либо новую зону целиком.

## 6. Почему читатель никогда не видит полу-запись

Шесть независимых механизмов, каждый из которых по отдельности закрывает свой класс гонок:

1. **Пространственное разделение.** Писатель не пишет в страницы, достижимые из активного meta: COW даёт новые номера страниц. Читатель физически не может прочитать изменяемую страницу — таких страниц нет.
2. **Единственная точка публикации — in-process атомик, а не скан meta.** Читатель на hot-path получает `txn` из атомарного указателя `active_txn`, который обновляется **после** полной записи meta (шаг 10 коммита). Meta-страницы читаются только при открытии/восстановлении. Поэтому частично записанная meta в page cache не может быть принята за состояние — читатель её просто не читает.
3. **Целостность meta как единицы.** При восстановлении meta валидируется CRC по всей странице; частично записанная meta не проходит проверку и игнорируется. Выбирается **max-valid meta** (§5.4). Один torn-слот при валидном втором — штатный крах (`torn_meta = true`, без `NEEDS_FSCK`); `NEEDS_FSCK` — если у битого слота декодируется `txnid >` выбранного (риск потерянного коммита); обе невалидны — `CorruptNoValidMeta`. Данные выбранной meta в `Sync`/`Flush` fsync'нуты до её записи, в `Memory` — требуют чистого отката на `≤ durable_watermark` либо `NEEDS_FSCK`/opt-in+read-only.
4. **Монотонность + двухфазный пин.** `txnid` строго возрастает; читатель публикует `T`, пере-проверяет `active_txn` и при расхождении откатывается **до** чтения данных (протокол `docs/spec/zonefile-v1.md` §6.3). «Передумать» на более старую мету нельзя.
5. **Удержание эпохи.** Пока читатель держит `T`, страницы, освобождённые при `txn ≤ T`, не выдаются (`oldest_reader_txn`); даже если писатель закоммитил `T+50`, граф `T` остаётся нетронутым. Учитывается и строгая граница `free_txn < durable_watermark` — иначе откат после краха мог бы попасть на переиспользованные страницы, ещё достижимые из `watermark−1`; принятие meta `T > durable_watermark` **не** повышает watermark (§5.2/§5.4).
6. **Порядок записи на носитель.** `fdatasync(данные)` предшествует записи meta; после краха meta `T` либо есть и её данные на диске, либо её нет.

**Для всех трёх режимов.** В `Sync` свойства 1–6 выполняются на диске, `durable_watermark` двигается каждым коммитом. В `Flush` свойства 1–6 выполняются на диске для данных, но meta не fsync'ится: после рестарта процесса все коммиты видны (page cache цел), после power loss возможен откат к последней долетевшей meta; watermark не двигается. `Flush` применим только до первого `sync()`: после него `durable_watermark > 1`, и липкий режим требует `Sync`, поэтому гарантия `Sync` не теряется последующими `Flush`. В `Memory` (`NOSYNC`) свойства 1–5 выполняются в пределах page cache, а свойство 6 — только при явном `sync()`; meta может пережить данные, поэтому recovery сначала чисто откатывается на meta `≤ durable_watermark`, иначе требует `NEEDS_FSCK` + `allow_unsynced_memory_recovery` и read-only до offline `fsck`. Полу-запись (смесь старого и нового) невозможна ни в одном режиме: видимость переключается одной метой, а граф `T` неизменяем.

Формально: множество страниц, достижимых из `meta(T)`, неизменно с момента публикации `T` до освобождения всех читателей `T` (инвариант I-4 в спецификации). Полу-запись означала бы страницу в графе `T`, изменённую позже `T` — что запрещено инвариантом.

## 7. Последствия

### 7.1. Положительные

- Коммит одной записи — десятки страниц, а не мегабайты; задержка правки не зависит от размера зоны (R1).
- Чтение полностью lock-free; `lookup` — спуск по дереву без единого атомарного RMW (R5).
- Zero-copy: `Rrset`/RDATA — срезы `mmap` (R4), пригодные и для UDP-ответа, и для AXFR-потока.
- Канонический порядок «бесплатно» даёт AXFR/NSEC/DNSSEC-подпись (R10).
- Нет журнала/WAL — меньше кода, меньше режимов отказа. Crash safety обеспечивается порядком записи и двойным meta.

### 7.2. Отрицательные / цена

- Нужны freelist, таблица читателей, `fsck`, детект утечек страниц — ~30% объёма крейта сверх «просто дерева».
- Файл фрагментируется; требуется периодическая дефрагментация (онлайн, по зоне — §7.4).
- Карта `mmap` фиксируется на открытии (`map_size`); рост сверх неё — только переоткрытием. Это плата за то, что срезы живут столько же, сколько `ZoneFile` (нельзя ремапить под живыми срезами).
- Два `fsync` на коммит в `Sync` — на дешёвом SATA это ~5–10 мс; отсюда group commit и режим `Flush`. `Flush` экономит второй fsync, но не двигает `durable_watermark`: при `durable_watermark = 1` переиспользование невозможно (`reclaim_txn = 0`), файл только растёт, поэтому нужен периодический `sync()`. Первый `sync()` необратимо переводит файл в липкий `Sync` — «постоянно слабый» режим с возвратом страниц невозможен по соображениям сохранности подтверждённых коммитов.
- Диагностика сложнее, чем у «перезапиши файл»: нужен `fsck` и внутренняя статистика.

### 7.2.1. Примечание о сборке (не о формате)

Репозиторий хранит `Cargo.lock` (в т.ч. для бинарников), чтобы сборка прототипа и бенчмарков была воспроизводима: версии `crc32c`, `memmap2`, `io-uring` и др. фиксируются, а сравнение метрик между прогонами не зависит от дрейфа зависимостей. Это проектное правило, к раскладке файла зон отношения не имеет.

### 7.3. Смягчение

- `map_size` — **параметр создания файла**, дефолт **4 GiB** (sparse: физически занимается только записанное). В тестах — 64–256 MiB. При исчерпании — `MapFull`, а не порча; файл продолжает обслуживать чтение.
- Контейнеры с квотой: `ftruncate` до 4 GiB sparse обычно не расходует квоту, но на ФС без sparse (или с `overlayfs` поверх квоты) возможен отказ. Поведение: старт с понятной ошибкой (`MapAllocFailed { size, errno, hint }`), без «тихого» урезания карты; оператор понижает `map_size` конфигом.
- Group commit (≤ 1 мс) выравнивает throughput при множестве мелких правок.
- Онлайн-дефрагментация по зоне не требует остановки сервера.

**Стратегия роста файла — отдельная задача, в M1 не реализуется.** Описана в `docs/spec/zonefile-v1.md` §3.1. В v1 `page_count_max` живёт только в неизменяемом superblock, поэтому рост = offline `zonefile compact --out --map-size=<new>` + `rename` + `reopen`; онлайн-рост (`ftruncate` + remap с полем `map_size` в meta, stop-the-world ≤ 1 мс на границе «нет живых снапшотов») — v1.1. До реализации рост невозможен: `MapFull`.

### 7.4. Компакция

Три уровня, по возрастанию стоимости:

1. **Merge/borrow/split страниц** при правках: split даёт 40–60% заполнения, последовательная загрузка (bulk) — до 90%, стабильная полоса 50–90%; underflow < 25%, merge только при объединении ≤ 75% (гистерезис против thrashing). Сепараторы родителя обновляются при borrow/merge/collapse (спецификация §13.4).
2. **Онлайн-перестройка одной зоны** (`compact_zone(zone)`): читает зону каноническим обходом и пишет её дерево в свежие страницы в одной транзакции, затем меняет `tree_root`. Ломает фрагментацию и пере-фронт-кодирует ключи. `zone_seq` не меняется. Требует ~1× размера зоны свободного места; сервер не останавливается.
3. **Offline-компакция в новый файл** (`zonefile compact --in --out`) + атомарный `rename` + переоткрытие. Для «сжать всё», смены `page_size` и `map_size`.
4. **Уборка tombstone-зон (GC)**: триггер — фоновая `gc_task` (интервал 300 с) или явный `compact_zone`; условие — `reclaim_txn ≥ deleted_txn`. Проход сканирует каталог O(Z), удаляет запись и освобождает дерево зоны и per-zone блок **в этом коммите** (`free_txn = txnid`). При удалении зоны страницы не освобождаются вообще; повторное создание того же origin освобождает старые страницы в своём коммите.

## 8. Отклонённые микрорешения

### 8.1. Один файл на зону

См. §3 E. Плюс: `fsync` на зону, изоляция порчи. Минус: нет согласованного снапшота между зонами (нужен для IXFR-out и для DNSSEC-подписи набора зон), тысячи дескрипторов, нет atomic swap «все зоны сразу».

### 8.2. `memcmp`-совместимые ключи (length-prefixed RLE)

Соблазнительно: сравнение ключей = `memcmp`. Но префикс-длина ломает канонический порядок RFC 4034: метки `"b"` (len 1) и `"aa"` (len 2) при сравнении длин дадут `"b" < "aa"`, тогда как канонически `"aa" < "b"` (0x61 < 0x62). Вариант с экранированием (`0x00 → 0x00 0x01`, терминатор `0x00 0x00`) корректен, но раздувает ключи и добавляет ветвление в компаратор. **Решение:** хранить компактный RLE и реализовать компаратор явно (≈ 8–20 нс на сравнение коротких имён). Компаратор вызывается ~10 раз на страницу при бинарном поиске — это ~100–200 нс, приемлемо, и он всё равно нужен для DNSSEC-канонизации и NSEC-обхода.

### 8.3. Компрессия имён в RDATA (name-refs)

Хранение `NS`/`MX`/`SRV`-целей как ссылок в name-таблицу экономит 15–30% объёма, но:

- ответ и AXFR требуют материализации RDATA в буфер → копия на каждый ответ, ломается R4;
- DNSSEC-канонизация требует несжатых имён → ещё один проход;
- ссылка делает значение зависимым от другой страницы → +1 cache miss и +1 точка порчи.

**Решение:** RDATA дословно, с инвариантом загрузчика (см. `docs/spec/zonefile-v1.md` §11.2), name-таблица как секция зарезервирована (`section id 2`) под v1.1, включается feature-флагом.

### 8.4. CRC32C против xxh3

| Критерий | CRC32C | xxh3 |
|---|---|---|
| Аппаратное ускорение | SSE4.2 `crc32` / ARMv8 `CRC32CX` — есть на всех целевых CPU | SIMD, ~10–30 GB/s |
| Скорость на 4 KiB | ~1–2 GB/s (≈ 2–4 µs/страница без оптимизации; 0.3–1 µs с 3-way) | ~20–40 GB/s (≈ 0.1–0.2 µs) |
| Гарантии обнаружения | все 1–2-битные, все burst ≤ 32 бит, полином стандартизован | вероятностные (64/128 бит), без структурных гарантий |
| Экосистема | ext4/btrfs/BCache, эталон для page checksum | хеш, не контрольная сумма |
| Проверка при чтении | кешируется: 1 раз на версию страницы | там же |

**Решение:** `crc32c` для страниц (структурные гарантии важнее скорости; стоимость амортизируется кешем проверок и записью «уже посчитано»). `xxh3`/BLAKE3 — только в опциональной секции манифеста (`section id 6`) для экспорта/verify. Детали — `docs/spec/zonefile-v1.md` §19.

### 8.5. Журнал (WAL) поверх B+tree

Даёт быстрый коммит (одна последовательная запись) и дешёвый recovery, но требует вторую подсистему (сегменты, checkpoint, replay, свой компактор). При COW-страницах журнал избыточен: коммит и так стоит O(depth). **Решение:** без WAL в v1; зарезервировано, если появится требование «много мелких коммитов в секунду» (> 20k/s), где 2 `fsync` станут узким местом.

## 9. Открытые вопросы

Статус: 1–4, 6, 7 закрыты; 5 требует подтверждения только форматной секции; 8–11 появились после ревью.

1. ~~**`map_size` по умолчанию.**~~ **Решено:** дефолт 4 GiB sparse, в тестах 64–256 MiB; при исчерпании — `MapFull`; рост (`ftruncate` + remap) — отдельный раздел спецификации (v1.1), в M1 не реализуется.
2. ~~**Межпроцессные читатели в v1.**~~ **Решено:** в M1 не требуются (один процесс, несколько потоков). Структура таблицы читателей и правила `LONG_HOLD`/`stale_reader_timeout` остаются в спецификации; тесты межпроцессного доступа — M3.
3. ~~**TTL-конфликты в RRset.**~~ **Решено (domain-model §2.5):** запись через API/DNS → `InvariantViolation(INV-1)`; импорт зоны / AXFR-in → `min(ttl)` + warning; DNSSEC-подпись TTL не меняет. Остаётся расхождение по **clamp vs маскирование** (см. 8).
4. ~~**`Durability::Flush` = `msync`?**~~ **Решено:** `Flush → MODE_NOMETASYNC`; `msync` на пути коммита не используется (§5.2). `domain-model.md` приведён к этому смыслу.
5. **NSEC3** — содержательно решено (`domain-model` §4.4): NSEC3-подпись реализована (SHA-1, Opt-Out = 0; NSEC3-для secondary вне объёма). Секция под NSEC3 в формате зарезервирована: `F_NSEC3` + `section id`.
6. ~~**Расхождение roadmap.**~~ **Уточнено Оркестратором:** формат обязан быть готов к DNSSEC в v1, крипто-пайплайн — M5; приёмка M1 — только форматная готовность (golden-тесты канонизации). `roadmap.md` не правится.
7. ~~**Лимит `max_rrsets` на зону.**~~ **Согласовано:** hard limit 50M, дефолт 10M (ADR 0004, SEC-ZF-005).
8. **TTL: clamp vs маскирование.** `domain-model` §2.6 маскирует старший бит и превращает `0x80000001` в `1`; спецификация требует clamp до `2^31−1` и `Corrupt(BadTtl)` при чтении. Нужно решение DDD-архитектора — иначе поведение на граничных TTL расходится между доменом и хранилищем.
9. **`WriteIntent` / `Edit` / `ApplyOutcome`** используются в `domain-model` §5.2, но не определены — блокер реализации TTL-политики и адаптера записи.
10. **`MAX_ZONE_META = 256 KiB`** требует отдельного лимита цепочки (65 страниц при 4096 против общего `MAX_OVERFLOW_PAGES = 64`) — в спецификации введён `MAX_ZONE_META_PAGES`; подтвердить имя константы в доменном контракте.
11. **`TooManyReaders` / `lookup_all` / `WrongAccessor`** — имена под доменный маппинг ошибок и аксессоры RRSIG; подтвердить, что `domain-model` использует ровно их.
